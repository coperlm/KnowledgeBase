    第五章 运输层（共 28 题：两座大楼里的秘书处传奇）

    1. 5-01 试说明运输层在协议栈中的地位和作用。运输层的通信和网络层的通信有什么重要区别？为什么运输层是必不可少的？

    • 【故事时间 / 说人话】： 想象北京有一座写字楼 A，上海有一座写字楼 B。每座写字楼里都有几十间办公室，里面坐着正在同时办公的员工（微信、浏览器、网易云音乐）。 网络层（IP） 就像是两座城市之间的邮政卡车司机：他只认识写字楼的大门地址（IP 地址），把一麻袋信件卸在一楼传达室就算完成任务，他根本不知道哪封信该送给 302 室的微信、哪封信该送给 508 室的浏览器，更不管路上丢没丢信。 这时候，每座写字楼里必须设立一个总秘书处（运输层）！秘书处给每个房间编上分机号（端口号），负责把各房间写好的信收拢打包交给卡车（复用），并在收到一麻袋信后按房间号精准送到每个员工桌上（分用），甚至替员工核对信件有没有缺页少字（可靠传输）。没有这个秘书处，整袋信堆在一楼大厅，楼里的员工谁也没法干活！
    • 【严谨考场结论】：
    • 地位与作用：运输层处于面向通信部分的最高层，同时也是用户功能中的最低层，向上面的应用层提供端到端的逻辑通信服务。
    • 核心区别（必考单选）：网络层是为主机之间提供逻辑通信（主机到主机）；而运输层是为运行在不同主机上的应用进程之间提供直接的逻辑通信（进程到进程 / 端到端）。
    • 为何必不可少：IP 层无法区分同一台主机上的不同应用进程（无端口分用与复用功能），且 IP 层只提供不可靠的尽最大努力交付，必须由运输层提供端口寻址及差错检错/可靠传输保障。

    2. 5-03 当应用程序使用面向连接的 TCP 和无连接的 IP 时，这种传输是面向连接的还是无连接的？

    • 【故事时间 / 说人话】： 你在网上包了一辆“门到门专属搬家服务”（TCP），搬家公司向你承诺：“先生您放心，您的100箱瓷器我们会按编号1到100完好无损、一箱不差地摆进您新家客厅！”至于搬家公司底下雇的100辆货车（IP数据报）在高速公路上到底走的是京沪高速还是沈海高速、哪辆车先开哪辆车后开，你完全看不见也不用管。对你（应用程序）而言，你享受到的就是实打实的专属连接服务；而在高速交警（路由器）眼里，路上跑的全是各自独立乱窜的无连接货车。
    • 【严谨考场结论】：这取决于从哪一层来看——在运输层（对应用程序而言）是面向连接的（通信前必须建立 TCP 连接，保证可靠按序交付）；但在网络层（对路由器而言）仍然是无连接的（每个封装了 TCP 报文段的 IP 数据报在互联网中独立选路传输）。

    3. 5-05 & 5-15 为什么有些应用愿意采用不可靠的 UDP 而不愿用可靠的 TCP（5-05）？使用 TCP 传实时话音会有什么问题？使用 UDP 传数据文件会有什么问题（5-15）？

    • 【故事时间 / 说人话】： 设想你正在跟异地恋女友打微信语音电话（实时话音）。突然网速卡了一下，你说了一句“我今天吃了红烧肉”里的“红”字丢包了。
    • 如果用 TCP（强迫症秘书）：秘书发现“红”字丢了，立刻拉响警报，死死拦住后面的“烧肉”不准播放，然后发信让对方重传“红”字。等0.5秒后重传的“红”字慢吞吞赶到时，你们的对话节奏早就乱成一团粥了！在实时通话里，少听半个字顶多“滋啦”一声，人脑自动就脑补过去了，迟到的声音比丢失的声音更可怕！
    • 反过来，如果你要给老板发一份 C 语言源代码文件或银行账单（数据文件），敢用 UDP（佛系快递员） 吗？路上只要丢掉 1 个字节的分号 ; 或者少个 0，整个程序就无法编译、账单金额直接差十倍！
    • 【严谨考场结论】：
    • 愿用 UDP 的应用（5-05）：①实时音视频/IP电话/视频会议（要求极低时延，宁可丢弃少量分组也不要迟到的重传分组）；②DNS、SNMP、DHCP、RIP（多为一次性短小请求/应答，不愿承受 TCP 三次握手建连时延与复杂状态开销）；③多播与广播应用（TCP 仅支持一对一单播，UDP 支持一对多）。
    • 用错协议的后果（5-15）：用 TCP 传实时话音会因超时重传和拥塞控制降速引入难以忍受的巨大时延与卡顿；用纯 UDP 传数据文件则会因丢包、乱序而无重传机制，导致接收端文件残缺损坏不可用。

    4. 5-06 & 5-07 接收方收到有差错的 UDP 数据报时如何处理（5-06）？如果应用程序非要用 UDP 完成可靠传输，这可能吗（5-07）？

    • 【故事时间 / 说人话】： UDP 这位佛系快递员发现包裹在路上摔烂了（检验和出错），他的处理原则只有四个字：“毁尸灭迹”——直接扔进垃圾桶（静默丢弃），既不告诉收件人，也不通知寄件人重发（5-06）。 那如果某家公司既贪图 UDP 不用排队握手的快速度，又非要保证包裹100%寄到，怎么办（5-07）？很简单！员工自己在信纸里编号、自己拿秒表计时、自己写收条！（比如现代大名鼎鼎的 HTTP/3 底层的 QUIC 协议，以及第6章的 TFTP 协议，就是在应用层自己写了一套确认和重传代码，架在 UDP 之上实现了可靠传输！）。
    • 【严谨考场结论】：
    • 5-06：接收方 UDP 发现检验和有差错时，直接将其静默丢弃（既不向上交付应用层，也不发回任何差错报告）。
    • 5-07：完全可能！ 但可靠传输不能靠 UDP 本身，而必须由应用程序自己在应用层实现确认（ACK）、编号、超时重传和流量控制等机制。

    5. 5-10 & 5-11 试说明运输层中伪首部的作用（5-10）。既然 UDP 和 IP 都是数据报，能否跳过 UDP 直接把应用数据交给 IP 层？UDP 提供了哪些 IP 没提供的功能（5-11）？

    • 【故事时间 / 说人话】： 有同学问：“UDP 就加了 8 个字节首部，跟 IP 一样不管死活往前扔，那应用层干脆跳过 UDP 直接把数据塞给 IP 层不就省了 8 个字节吗？”（5-11） 万万不可！如果跳过 UDP 直接塞给 IP，包裹到了对方大楼传达室（IP 层），传达室大爷看着包裹傻眼了：“这上面只写了我们大楼的 IP 地址，没写房间号（端口号）啊！我到底该送给 QQ 还是送给浏览器？” 至于“伪首部”（5-10），更是个绝妙的设计：UDP/TCP 秘书在算检验和时，偷偷把外层信封上的“寄件大楼 IP、收件大楼 IP、协议号”抄在一张临时小纸条（12字节伪首部）上一起算进检验和里，算完就把小纸条撕掉不发出去。等到了对方秘书手里，对方秘书也抄下外层信封上的 IP 地址凑上小纸条再算一遍——这样一来，哪怕邮递员把信送错了大楼（目的 IP 在路由途中被改错），或者把 TCP 信误当成 UDP 信，秘书在核对检验和时当场就能抓包报错！
    • 【严谨考场结论】：
    • 5-10（伪首部作用）：12 字节伪首部仅在计算运输层（UDP/TCP）检验和时临时添加（既不向下传送也不向上递交），目的是双重核验：既检查本层数据报在传输中是否出错，又验证 IP 层是否将该分组正确递交到了正确的目的主机 IP 地址和正确的运输层协议（防止 IP 首部地址或协议字段被篡改误投）。
    • 5-11（为何不能跳过 UDP）：不能跳过！ 因为 IP 层只能把数据报送到目的主机，无法区分主机内的不同应用进程。UDP 提供了 IP 层所没有的两大核心功能：①16位端口号（实现应用进程的复用与分用）；②对整个数据报（含数据载荷）的差错检验和（IPv4 首部检验和只检验 IP 首部，不检验数据部分）。

    6. 5-16 & 5-17 & 5-18 停止-等待协议的“踩坑进化三部曲”：

    • (1) 5-16：如果不使用编号是否可行？
    • (2) 5-17：收到重复报文段时悄悄丢弃而不发确认是否可行？
    • (3) 5-18：为什么只有 0/1 交替编号在报文长期滞留时依然会失败？
    • 【故事时间 / 说人话】： 这是一部通信工程师被网络丢包折磨出来的血泪进化史：
    • 第一集（不给包裹编号的惨案，5-16）：A 给 B 寄了一箱苹果。B 收下吃了，给 A 寄回一张收条（ACK）。结果收条在半路被风刮跑了！A 等不到收条，以为苹果没寄到，于是又补发了一箱一模一样的苹果。因为箱子上没贴序号，B 收到第二箱时欢天喜地以为是 A 今天新送的第二批苹果，又收下了！结果 A 只想发 1 箱，B 却收了 2 箱重复数据！
    • 第二集（收到重复包裹不回话的死锁，5-17）：吸取教训后，箱子贴上了序号 M0。A 发了 M0，B 收下并回发收条，结果收条又在半路丢了！A 超时重发 M0。B 一看：“咦？M0 我刚才收过了呀！”于是 B 把重发的 M0 扔进垃圾桶，但懒得再给 A 回一张收条。这下完蛋了——A 永远收不到 M0 的收条，就会天荒地老地每隔 5 秒给 B 重发一次 M0，双方彻底卡死在 M0 上！
    • 第三集（幽灵旧包裹借尸还魂，5-18）：B 终于学会了“收到重复 M0 也要补发收条”。但只用 0 和 1 两个序号轮流用还是出事了：A 先发了 M0，结果这个 M0 卡在某个拥堵的路由器里昏睡了半分钟。A 超时重发了第二个 M0，这次收条也迟到了，A 又重发……等后来 A 和 B 顺利传完了 M0、传完了 M1，轮到下一轮发全新的 M0 时，新 M0 半路丢了，而半分钟前昏睡的那个“老古董 M0”恰好醒过来跑到了 B 面前！ B 正等着收新一轮的 M0 呢，一看序号是 0，当场把上辈子的旧数据当成这辈子的新数据收下了！（这就是为什么 TCP 必须用长达 32 位的序号，并规定最大报文段寿命 MSL！）。
    • 【严谨考场结论】：
    • 5-16：不可行！ 当数据分组正确到达接收方、但返回的确认（ACK）丢失时，发送方会超时重传该分组；若无编号，接收方无法分辨这是“重传的旧分组”还是“新的下一分组”，会导致重复接收。
    • 5-17：不可行！ 接收方收到重复分组说明自己上次发出的确认（ACK）在途中丢失了；若只丢弃重复分组而不重发确认，发送方将永远收不到该分组的确认，从而陷入无限次重传该分组的死锁状态。
    • 5-18：交互过程为：A 发旧 \(M_0\)（滞留） \(\rightarrow\) A 超时重传 \(M_0\) \(\rightarrow\) B 收到重传的 \(M_0\) 并回迟到的 \(\text{ACK}_0\) \(\rightarrow\) A 收到 \(\text{ACK}_0\) 后发 \(M_1\)，B 收下回 \(\text{ACK}_1\) \(\rightarrow\) A 发送新一轮的 \(M_0\)（途中丢失） \(\rightarrow\) 最初滞留的旧 \(M_0\) 此时到达 B，B 误将其当作新 \(M_0\) 收下并回 \(\text{ACK}_0\)，导致协议出错。

    7. 5-25 & 5-26 & 5-27 & 5-28 & 5-29 TCP 首部设计的五个精巧机关：

    • (1) 5-25：为什么把 TCP 端口号放在最开始的 4 个字节？
    • (2) 5-26：为什么 TCP 有首部长度字段而 UDP 没有？
    • (3) 5-27：一个 TCP 报文段的数据部分最多为多少字节？若用户数据超过序号字段最大编号还能用 TCP 传吗？
    • (4) 5-28：A 向 B 发信源端口 \(m\)、目的端口 \(n\)，B 回信时源和目的端口是什么？
    • (5) 5-29：为什么丢了一个确认报文段，也不一定会引起对应数据的重传？
    • 【故事时间 / 说人话】：
    • 5-25（救命的前 4 字节）：当一个 IP 数据报在路上不幸夭折（比如 TTL 减到 0 或目的端口不可达）时，路由器会发回一张 ICMP 差错报告单。为了省流量，ICMP 规定只把夭折数据报的“IP 首部 + 里面载荷的前 8 个字节”复印贴在报告单上寄回给源主机。TCP 和 UDP 设计师心有灵犀地把源端口（2B）和目的端口（2B）全都放在了最开头的 4 个字节！这样源主机一拿到这 8 字节残骸，前 4 个字节一看就知道该去通知哪个端口的应用程序报错！
    • 5-26（定长制服 vs 伸缩背包）：UDP 首部永远是死板的 8 个字节，一量就知道第 9 个字节开始是数据；而 TCP 首部除了 20 字节基本款，后面还能挂 \(0 \sim 40\text{ B}\) 的扩展选项背包，所以必须有个“首部长度（数据偏移）”字段告诉接收方数据从哪儿开始。
    • 5-27（套娃限高与钟表转圈）：TCP 装在 IP 数据报肚子里，IP 总长度字段只有 16 位（最大 \(65535\text{ B}\)），扣掉 \(20\text{ B}\) IP 首部和 \(20\text{ B}\) TCP 首部，TCP 数据部分顶天只能装 \(65495\text{ B}\)！至于文件超过 \(2^{32}\text{ B}\)（\(4\text{ GB}\)）怎么办？就像家里的钟表只有 12 个数字却能记录一万年一样，序号用完 \(2^{32}-1\) 后直接绕回 \(0\) 循环使用，只要旧字节早已在网里消失，傳多大的文件都没问题！
    • 5-28 & 5-29（回信地址对调与后来居上的收条）：B 给 A 回信自然把源端口设为 \(n\)、目的端口设为 \(m\)（5-28）。而 TCP 的确认号是“累积确认”（比如 ack=500 意思是 500 以前的我全收到了！），就算之前 ack=200 的收条在路上丢了，只要在超时前 ack=500 的收条及时赶到，发送方一看“连 500 都收到了，200 肯定早到了”，就根本不会重传（5-29）！
    • 【严谨考场结论】：
    • 5-25：为了配合 ICMP 差错报告报文（仅封装出错 IP 数据报首部及其数据载荷的前 8 字节）和防火墙/NAT 快速读取端口，将源端口和目的端口放在最前 4 字节可使源主机根据 ICMP 报文准确找到对应的应用进程端口。
    • 5-26：UDP 首部长度固定为 \(8\text{ B}\)，无需字段指明；TCP 首部包含可变长度的选项字段（总长在 \(20\text{ B} \sim 60\text{ B}\) 之间变化），必须用 4 位“数据偏移（首部长度）”字段指明数据载荷的起始位置。
    • 5-27：最多为 \(65495\text{ B}\)（\(= 65535 - 20\text{ B IP首部} - 20\text{ B TCP首部}\)）。若用户数据超过 \(2^{32}\text{ B}\)，依然可以用 TCP 传送，因为序号按模 \(2^{32}\) 循环绕回使用（只要旧序号报文段已超过 MSL 在网络中消失，或启用时间戳选项防绕回 PAWS）。
    • 5-28：B 向 A 发送回信时，源端口是 \(n\)，目的端口是 \(m\)。
    • 5-29：因为 TCP 采用累积确认机制。若前一个确认丢失，但在重传计时器超时之前，发送方收到了后续报文段的更高序号确认（表明此前所有数据均已按序收到），就不会触发重传。

    8. 5-32 什么是 Karn 算法？若不采用 Karn 算法，重传时间最后会减小到什么程度？

    • 【故事时间 / 说人话】： 想象你给朋友寄信，平时一去一回要 10 天（\(\text{RTT}=10\)）。有一次信在路上堵了，你等了 15 天没回音，就在第 15 天早上一口气补寄了第二封信。结果当天下午（仅过了 0.1 天），邮递员送来了一封回信！ 这时候世纪难题来了：这封回信到底是针对 15 天前第一封信的（真实 \(\text{RTT}=15.1\) 天），还是针对今天早上刚寄出的第二封信的（虚假 \(\text{RTT}=0.1\) 天）？ 如果不采用 Karn 算法（凡是重传过的报文段，一律不准用来测量 RTT，且每重传一次把 RTO 翻倍），而是傻乎乎地认为每次收到的回信都是对刚发出的重传报文的回应，你就会误以为“哇！现在邮局只要 0.1 天就能来回！”，于是把超时时间 RTO 改成 0.2 天 \(\rightarrow\) 下次 0.2 天一到又超时重传 \(\rightarrow\) 刚重传又收到上一轮的回信 \(\rightarrow\) 又以为只要 0.01 天……如此恶性循环，最后重传时间 RTO 会无限减小趋近于 \(0\)！
    • 【严谨考场结论】：
    • Karn 算法核心：在计算加权平均 \(\text{RTT}_S\) 时，只要报文段重传了，就不采用其往返时间样本（以消除确认二义性）；且每重传一次，就把超时重传时间 \(\text{RTO}\) 增大一些（典型做法是令 \(\text{新 RTO} = 2 \times \text{旧 RTO}\)）。
    • 不采用 Karn 算法的后果：发送方每次重传后很快收到原报文段的迟到确认，误将其当作重传报文段的确认，算出的 \(\text{RTT}\) 样本极小，导致重传时间 \(\text{RTO}\) 不断减小，最终趋近于 \(0\)（或系统允许的最小极限值），引发灾难性的无效重传风暴。

    9. 5-42 & 5-43 & 5-44 TCP 连接建立与释放的三个特殊剧本：

    • (1) 5-42：在四报文挥手中，被动关闭方 B 收到 A 的 FIN 后，能否先不发 ACK，等后面连同 B 自己的 FIN 一起发？
    • (2) 5-43：在什么情况下会发生从状态 SYN-SENT 到状态 SYN-RCVD 的变迁？
    • (3) 5-44：试以具体例子说明为什么一个运输连接可以有多种方式释放。
    • 【故事时间 / 说人话】：
    • 5-42（为什么挥手要分四步而不是三步）：A 对 B 说：“我的话说完了，我要挂电话了（FIN）！”这时候 B 手里可能还有一大段话没说完（半关闭状态）。如果 B 闷声不吭，非要等自己把剩下10分钟的话全说完、发自己的 FIN 时才顺带确认 A 的 FIN，那 A 在这 10 分钟里没收到确认，会以为自己的 FIN 丢了，每隔几秒就狂吼一声“我要挂了！我要挂了！”。所以 B 必须先礼貌地回一句“知道了你先别说话了（ACK）”，等自己忙完了再发“我也说完了（FIN）”。
    • 5-43（心有灵犀的“同时打开”）：平时都是客户追服务器（三报文握手）；但万一两台主机在同一毫秒、用刚好配对的端口互相向对方发出了 SYN 建连请求呢？双方发出 SYN 后都进入 SYN-SENT 状态，紧接着在半路擦肩而过收到对方的 SYN，于是双方同时惊讶地变迁进入 SYN-RCVD 状态！这叫 TCP 同时打开（Simultaneous Open，注意：此时也是只建立 1 条连接，而不是 2 条！）。
    • 5-44（好聚好散 vs 拔网线硬断）：正常情况下双方四次挥手优雅告别；如果 B 收到 A 的 FIN 时自己恰好也没数据要发了，可以把第 2 步 ACK 和第 3 步 FIN 合并成 1 个包发出去（变成三报文挥手）；万一对方电脑突然断电或网线被挖掘机铲断，几次重传无果后只能靠超时定时器强行单方面关闭，或者发 RST（复位）强行断开。
    • 【严谨考场结论】：
    • 5-42：一般不能省略第 2 步单独的 ACK！ 因为被动关闭方 B 收到 FIN 进入半关闭状态后，其应用进程可能还有大量数据需要继续发送，要过较长时间才会发出自己的 FIN；若不立即发回 ACK，主动关闭方 A 会因超时而不断重传 FIN 报文段。（仅当 B 恰好也没有数据要发、能立即发出 FIN 时，才可将第2、3步合并为 FIN+ACK）。
    • 5-43：发生在通信双方同时主动向对方发起连接请求（即“同时打开” Simultaneous Open）的情况下——本端发出 SYN 后处于 SYN-SENT 状态，在收到对方 ACK 之前先收到了对方发来的 SYN 报文段，于是发送 SYN+ACK 并进入 SYN-RCVD 状态。
    • 5-44：运输连接释放有多种方式：①正常的四报文双方优雅释放；②当被动方无数据要发时合并第2、3步的三报文释放；③一方崩溃或链路中断，另一方经多次超时重传失败后超时强制释放；④一方发送 RST（复位报文段）异常立即中断连接。

    10. 5-50 & 5-52 & 5-53 & 5-57 UDP 检验和与长度极限四连问：

    • (1) 5-50：图 5-6 计算 UDP 检验和的例子如何手算验证？
    • (2) 5-52：UDP 和 IP 的不可靠程度是否相同？
    • (3) 5-53：UDP 用户数据报的最小长度是多少？构成的最短 IP 数据报是多长？
    • (4) 5-57：某客户有 \(67000\text{ B}\) 的分组，怎样使用 UDP 传送？
    • 【故事时间 / 说人话】：
    • 5-50：把 12 字节伪首部 + 8 字节 UDP 首部 + 数据部分（奇数个字节末尾补 1 字节全 0）按每 16 位一行对齐，用二进制反码加法（最高位进位回卷加到最低位）求和，最后按位取反即得书上的 11110110 11101101。
    • 5-52：虽然 IP 和 UDP 都叫“无连接不可靠”，但 IP 老兄连包裹里的货物（数据部分）看都不看一眼，只检查外包装盒面单（IP 首部检验和）；而 UDP 至少会把里面的货物也过一遍秤（检验整个 UDP 数据报），一旦货物歪了直接拒收丢弃，不会把脏数据喂给应用程序。
    • 5-53 & 5-57（最小空盒子与最大爆仓盒子）：UDP 最小可以装 \(0\text{ B}\) 数据，只发 \(8\text{ B}\) 的空首部，套上 \(20\text{ B}\) IP 首部就是 \(28\text{ B}\)（5-53）。反过来，客户想一口气塞 \(67000\text{ B}\) 给 UDP（5-57）？门儿都没有！因为 UDP 首部的“总长度”字段只有 16 位（最大只能表示 \(65535\text{ B}\)），而且底下的 IP 数据报总长也受 16 位限制（扣除 \(20\text{ B}\) IP 首部和 \(8\text{ B}\) UDP 首部后，单次最多只能装 \(65507\text{ B}\) 数据）。所以客户必须在应用层自己拿菜刀把 \(67000\text{ B}\) 切成两块（例如一块 \(60000\text{ B}\)、一块 \(7000\text{ B}\)），分两次调用 UDP 发送！
    • 【严谨考场结论】：
    • 5-50：将伪首部、UDP 首部及填充对齐的数据按 16 位字进行二进制反码求和（进位回卷），结果按位取反后与教材图 5-6 完全一致。
    • 5-52：不完全相同。IP 的不可靠体现在跨网络路由时可能丢包、乱序、重复，且 IPv4 只检验首部而不检验数据载荷；UDP 虽然也不保证交付和顺序，但 UDP 检验和覆盖了整个 UDP 首部与全部数据载荷，能保证向上交付给应用进程的数据块本身是没有比特差错的。
    • 5-53：UDP 用户数据报最小长度为 \(8\text{ B}\)（仅含首部，数据为 \(0\text{ B}\)）；构成的最短 IP 数据报长度为 \(8 + 20 = \mathbf{28\text{ B}}\)。
    • 5-57：由于 UDP 首部 16 位长度字段最大为 \(65535\text{ B}\)，且受 IP 首部 16 位总长度字段限制，单个 UDP 数据报最多只能携带 \(65535 - 20 - 8 = \mathbf{65507\text{ B}}\) 的应用数据。因此 \(67000\text{ B}\) 不能放入单个 UDP 数据报中，必须由客户应用程序先将其拆分为两个（或多个）小于 \(65507\text{ B}\) 的较小数据块，再分别封装成两个独立的 UDP 数据报发送（且如果超过链路 MTU，在 IP 层还会继续分片）。

    11. 5-63 & 5-64 TCP 有限状态机（图 5-30）进阶走迷宫：

    • (1) 5-63：TCP 连接处于 SYN-RCVD 状态，相继发生：(1) 应用程序发送“关闭”报文；(2) 收到 FIN 报文段。写出每次事件后的状态与动作。
    • (2) 5-64：TCP 连接处于 FIN-WAIT-1 状态，相继发生：(1) 收到 ACK 报文段；(2) 收到 FIN 报文段；(3) 发生了超时。写出每次事件后的状态与动作。
    • 【故事时间 / 说人话】：
    • 5-63（刚答应握手就反悔，还撞上对方也反悔）：本端刚收到 SYN 处于 SYN-RCVD 状态，还没等握手彻底完成，本端应用突然反悔喊“关闭！”（事件1）\(\rightarrow\) 本端立刻发出 FIN 报文段，跨步进入 FIN-WAIT-1 状态；紧接着还没收到自己 FIN 的确认，迎面却收到了对方也发来的 FIN 报文段（事件2，双方同时关闭！）\(\rightarrow\) 本端立即发回 ACK 确认报文段，状态变迁进入 CLOSING 状态！
    • 5-64（最经典的客户端主动关闭三步曲）：本端已发出 FIN 处于 FIN-WAIT-1 状态：
      1. 收到对方对 FIN 的 ACK 报文段 \(\rightarrow\) 不发送任何报文（无动作），状态进入 FIN-WAIT-2（耐心等对方发 FIN）；
      2. 收到对方发来的 FIN 报文段 \(\rightarrow\) 向对方发回 ACK 确认报文段，并启动 \(2\text{MSL}\) 时间等待计时器，状态进入 TIME-WAIT；
      3. 发生了超时（即 \(2\text{MSL}\) 计时器时间到）\(\rightarrow\) 释放连接控制块 TCB（无报文发送），状态最终进入 CLOSED！
    • 【严谨考场结论】：
    • 5-63 标准答案：
      • 事件 (1) 后：动作为 发送 FIN 报文段；状态变为 FIN-WAIT-1。
      • 事件 (2) 后：动作为 发送 ACK 确认报文段；状态变为 CLOSING。
    • 5-64 标准答案：
      • 事件 (1) 后：动作为 无（继续等待对方的连接释放报文段）；状态变为 FIN-WAIT-2。
      • 事件 (2) 后：动作为 发送 ACK 确认报文段，并设置 \(2\text{MSL}\) 计时器；状态变为 TIME-WAIT。
      • 事件 (3) 后：动作为 无（清除连接资源）；状态变为 CLOSED。

    12. 5-72 & 5-73 TCP 接收窗口的“契约精神”：为什么绝对不允许窗口前沿向后收缩？

    • 【题目设问】：已知 TCP 接收窗口大小是 \(600\)，已确认序号是 \(300\)（即当前允许发送的窗口范围是 \(300 \sim 899\)，窗口前沿在 \(900\)）。5-72 问在不断收发过程中，接收窗口可能会增大或缩小吗？举例说明哪些情况允许、哪些不允许。5-73 问若接收方突然不能再收数据了，立即发 ack = 300, rwnd = 0 使窗口前沿从 \(900\) 后退到 \(300\)，这是否允许？
    • 【故事时间 / 说人话】： 这叫 TCP 滑动窗口的“君子一言，驷马难追（严禁前沿后退）”铁律！ 接收方 B 刚才给发送方 A 发了一张支票（ack = 300, rwnd = 600），意思是：“300 号以前的货我收齐了，我现在仓库空着 600 个位置，允许你把 300 号一直到 900 号以前的货全发过来！” A 一拿到这张许可，可能已经在第 1 毫秒把 300～899 号货物全都装车发到高速公路上了！ 这时候如果 B 突然反悔，发个 ack = 300, rwnd = 0（把原本设在 900 的窗口右边界/前沿强行拉回到 300，这叫“窗口前沿后退 / 收缩窗口”，5-73），那已经在高速路上狂奔的 300～899 号货车怎么办？撞墙销毁吗？ 所以 TCP 国际标准立下死规矩：接收窗口的大小 rwnd 可以变大，也可以变小，但有一个绝对底线——窗口的右边界（前沿 \(= \text{ack} + \text{rwnd}\)）只能原地不动或向前推进，绝对不允许向后倒退！ 如果 B 真的想把窗口缩小到 \(0\)，它必须老老实实先把当初承诺的这 600 字节收进来（即一边讓 ack 往前加，一边让 rwnd 同步减小，比如发 ack = 500, rwnd = 400，前沿始终死死钉在 \(500 + 400 = 900\) 不后退！）。
    • 【严谨考场结论】：
    • 5-72（允许与禁止的情况）：初始状态为 ack = 300, rwnd = 600（窗口前沿在 \(300 + 600 = 900\)）。接收窗口的大小本身是可以增大或缩小的，但必须保证新的窗口前沿 \((\text{ack}_{\text{新}} + \text{rwnd}_{\text{新}}) \ge \text{旧窗口前沿 } 900\)：
      • 可能发生（允许）的情况：①窗口增大或前移，如发 ack = 400, rwnd = 600（前沿移至 \(1000\)）或 ack = 300, rwnd = 700（前沿移至 \(1000\)）；②窗口缩小但前沿不后退，如收到 \(200\text{ B}\) 数据后缓存未腾出，发 ack = 500, rwnd = 400（窗口虽从 \(600\) 缩小为 \(400\)，但前沿仍在 \(500 + 400 = 900\) 未后退，完全合法！）。
      • 不允许发生（禁止）的情况：任何导致新窗口前沿 \(< 900\)（即窗口前沿向后收缩）的通告，如发 ack = 300, rwnd = 500（前沿退至 \(800 < 900\)）或 ack = 400, rwnd = 400（前沿退至 \(800 < 900\)）。
    • 5-73：绝对不允许！ 因为发送方可能已经根据上次通告的窗口发出了序号 \(300 \sim 899\) 的数据，TCP 标准强烈不赞成（禁止）使窗口前沿向后收缩的操作。

    13. 6-01 & 6-02 互联网的域名结构与电话号码结构有何异同（6-01）？DNS 四类域名服务器有何区别（6-02）？

    • 【故事时间 / 说人话】：
    • 6-01（倒着写的地址 vs 正着写的电话号）：我们写固定电话号码是“从大到小”（+86 中国 - 25 南京 - 8379xxxx 东南大学），而且电话局交换机看到 025 就知道往江苏省铜线走（号码跟物理地理位置死死绑定）。而互联网域名偏偏是“从小到大倒着写”（www.seu.edu.cn：最左边 www 是具体主机，最右边 .cn 才是最大的顶级域名），而且域名只看逻辑归属、跟物理地理位置毫无关系——哪怕把 seu.edu.cn 的服务器搬到美国机房，域名一个字母都不用改！
    • 6-02（四个级别的问路向导）：你电脑想查一个陌生网址时，先问你们学校/运营商的本地域名服务器（你的贴身秘书）；秘书查不到就去问全球最高层的根域名服务器（掌管全球顶级目录的总管）；总管说“.cn 的事你去问中国馆长”，这就是顶级域名服务器；中国馆长说“seu.edu.cn 的花名册在东南大学网络中心手里”，最后找到的这位掌握最终 IP 底牌的，就叫权限域名服务器！
    • 【严谨考场结论】：
    • 6-01：相同点是均采用层次树状结构以保证全球唯一性；不同点在于：①电话号码是左大右小（国家码在最左），而域名是左小右大（最高级别顶级域名在最右，级别最低的主机名在最左）；②电话号码与物理地理位置及交换机拓扑严格绑定，而域名仅反映逻辑组织管理层次，与物理地理位置和 IP 拓扑无关。
    • 6-02：DNS 主要功能是将便于人记忆的域名转换为机器用于路由的 IP 地址。四类服务器区别：
      1. 根域名服务器：最高层次，知道所有顶级域名服务器的域名和 IP 地址；
      2. 顶级域名服务器（TLD）：负责管理在该顶级域名（如 .com、.cn、.edu）下注册的所有二级域名；
      3. 权限域名服务器：负责一个特定“区（Zone）”的域名解析，保存该区内主机的最终域名与 IP 映射记录；
      4. 本地域名服务器（默认 DNS）：不属于上述三级域名树层次结构，但离用户最近，当主机发起查询时首先替主机代为向上述三级服务器进行迭代查询并缓存结果。

    14. 6-08 一口气串起万维网（WWW）的 12 个核心术语：

    • 【故事时间 / 说人话】： 1989 年欧洲核子研究中心的蒂姆·伯纳斯-李发明了万维网（WWW）。在这个世界里： 如果一篇文章里带了能点击跳转到另一篇文章的链接（超链 Hyperlink），这种纯文字网状文档就叫超文本（Hypertext）；要是里面还塞了图片、音频和视频，就升级叫超媒体（Hypermedia）。 为了解决三个核心问题，他发明了万维网三剑客：
    • 怎么给全世界的每个页面编个唯一门牌号？用 URL（统一资源定位符：协议://主机:端口/路径）；
    • 你的电脑（客户端软件叫浏览器 Browser）怎么向服务器要这个页面？用 HTTP（超文本传送协议）；
    • 拿回来的文档怎么排版显示成漂亮的图文页面（Page）？用 HTML（超文本标记语言）！ 后来大家嫌静态网页太死板，想在网页上查实时股票或提交表单，于是让后台服务器收到请求后临时跑一段程序生成网页，这个后台接口标准就叫 CGI（通用网关接口）；再后来，干脆把一小段脚本代码（如 JavaScript）直接发给你的浏览器，让网页在你电脑屏幕上自己动起来，这就叫活动文档（Active Document）。最后网页多到几十亿个找不过来，于是诞生了百度、Google 这样的搜索引擎（Search Engine）！
    • 【严谨考场结论（英文缩写原文速记）】：
    • WWW：World Wide Web（万维网，大规模联机式信息储藏所）；
    • URL：Uniform Resource Locator（统一资源定位符，唯一标识互联网上资源的位置）；
    • HTTP：HyperText Transfer Protocol（超文本传送协议，万维网客户与服务器间的应用层交互协议）；
    • HTML：HyperText Markup Language（超文本标记语言，描述网页结构与排版显示的语言）；
    • CGI：Common Gateway Interface（通用网关接口，定义了动态文档如何创建以及数据如何输入给后台服务端应用程序的接口标准）。

    15. 6-13 浏览器同时打开多个并行 TCP 连接进行浏览的优缺点如何？

    • 【故事时间 / 说人话】： 你去超市买 10 件商品。如果只排 1 个收银台（单条 TCP 连接），要一件件扫码；如果你把七大姑八大姨叫来，一口气同时霸占 6 个收银台并行结账（浏览器同时打开多个 TCP 连接），你的结账速度当然瞬间起飞，网页图片刷刷地同时蹦出来！ 但超市老板和其他顾客就不干了：第一，世界上总共就 10 个收银台，你一个人占了 6 个，相当于在网络发生拥塞时变相抢占了 6 倍的带宽份额，对其他老实只开 1 条连接的应用极不公平，甚至加剧网络拥塞；第二，服务器同时维护成千上万个并行 TCP 连接，内存和 CPU 负担也会成倍暴增！
    • 【严谨考场结论】：
    • 优点：缩短网页的整体加载响应时间（可并行下载网页中的多个内嵌图片/脚本对象，减少往返等待时延 RTT，并在竞争链路中获得更大比例的带宽）。
    • 缺点：①同时建立多条 TCP 连接会发送大量握手与控制报文，加重万维网服务器的内存与 CPU 开销；②相当于成倍绕开了单条 TCP 的拥塞控制限制，挤占其他正常用户的带宽，加剧互联网拥塞。

    16. 6-23 & 6-31 简述 SMTP 通信的三个阶段（6-23）。基于万维网的电子邮件系统（网页邮箱）有什么特点？传送邮件时使用什么协议（6-31）？

    • 【故事时间 / 说人话】：
    • 6-23（邮递员交接班三部曲）：SMTP 发邮件就像两位极其讲礼貌的绅士打电话：①连接建立（先拨通 25 端口 TCP，互相报家门 HELO，绝不通过中间别的邮件服务器中转，必须直连！）；②邮件传送（报寄件人 MAIL FROM \(\rightarrow\) 报收件人 RCPT TO \(\rightarrow\) 喊一声 DATA 开始传正文，以单独一行句号 . 结束）；③连接释放（喊一声 QUIT 挂断 TCP）。
    • 6-31（必考高频坑点：用浏览器登网页版邮箱发邮件，到底用的啥协议？）： 很多同学一看到“发邮件”就无脑选 SMTP——错！当你不用 Outlook 客户端，而是直接打开 Chrome 浏览器登录 mail.163.com 和朋友收发邮件时：你电脑的浏览器和 163 网站之间无论是写信发送、还是点开读信，走的统统是万维网的 HTTP（或 HTTPS）！只有当 163 服务器把你的信跨网转寄给对方的 QQ 邮箱服务器时，两台服务器之间才用 SMTP！
    • 【严谨考场结论】：
    • 6-23（SMTP 三阶段）：①连接建立（发件人邮件服务器与收件人邮件服务器直接建立 TCP 连接，发出 HELO 命令）；②邮件传送（依次使用 MAIL FROM、RCPT TO、DATA 命令传输邮件首部与内容）；③连接释放（发送完毕后发 QUIT 命令释放 TCP 连接）。
    • 6-31（基于万维网的邮件系统协议——必背！）：特点是用户无需在电脑上安装专用的邮件客户端软件（UA），只需使用普通浏览器即可随时随地收发管理邮件。所使用的协议为：
      • 用户浏览器 \(\rightarrow\) 发送方邮件服务器（发信）：使用 HTTP（或 HTTPS）；
      • 发送方邮件服务器 \(\rightarrow\) 接收方邮件服务器（服务器间投递）：使用 SMTP；
      • 接收方邮件服务器 \(\rightarrow\) 用户浏览器（读信）：使用 HTTP（或 HTTPS）（而非 POP3/IMAP！）。

    17. 6-33 & 6-34 什么是网络管理？解释：网络元素、被管对象、管理进程、代理进程。

    • 【故事时间 / 说人话】： 现代网络里有成千上万台不同厂家生产的路由器、交换机、服务器，这些设备统称为网络元素（网元）。如果哪根网线断了、哪台路由器 CPU 飙到 \(100\%\) 了，总不能让网管员跑遍全楼一间间机房去摸机器吧？ 于是我们在监控中心设一台大电脑运行管理进程（Manager，总司令）；并在每一台路由器、交换机肚子里驻留一个小后台程序叫代理进程（Agent，潜伏哨兵）；把每台设备里需要监控的“端口状态、错包计数器、路由表项”抽象成一个个变量，叫被管对象（Managed Object）。总司令坐在办公室发个指令给哨兵，就能读写全网所有设备的状态，这就是网络管理！
    • 【严谨考场结论】：
    • 6-33（网络管理定义）：对网络中各种软硬件设备的运行状态进行监测、控制、配置、故障排查与性能优化，使网络能高效、可靠、安全地运行。
    • 6-34（四大术语）：
      1. 网络元素（Network Element，网元）：网络中被管理的各种具体设备（如路由器、交换机、集线器、主机等）；
      2. 被管对象（Managed Object）：每一个网络元素中可以被管理的具体硬件部件或软件配置参数变量（如某个接口的速率或丢包计数），统一存放在 MIB 库中；
      3. 管理进程（Manager）：运行在网络管理工作站（管理站）上的客户端主控程序，负责发起管理命令并接收告警；
      4. 代理进程（Agent）：运行在每一个被管网络元素（设备）上的服务端后台程序，负责听从管理进程指令去读写本地的被管对象，并在异常时主动向管理进程发送 Trap 告警。

    第七章 网络安全（共 6 题：间谍、防伪印章与通行证的故事）

    18. 7-03 & 7-12 为什么网络安全不仅局限于机密性（7-03）？举例说明：(1)既需保密又需鉴别；(2)只需保密不需鉴别；(3)不需保密但需鉴别（7-12）。

    • 【故事时间 / 说人话】：
    • 7-03（光锁进保险箱就能高枕无忧吗？）：假定你去银行给骗子汇了 100 块钱，银行把这笔指令用最顶级的密码锁进了铁盒（绝对机密，骗子根本打不开盒子看不懂里面写的啥）。但骗子根本不需要打开盒子！骗子在半路把这个铁盒完整复印了 100 份，每隔 1 秒往银行柜台扔一个一模一样的铁盒（重放攻击），银行打开一看全是合法密文，当场从你账上划走了 100 次 100 块！又或者骗子干脆用一万台机器把银行大门堵死（DoS 拒绝服务攻击）。你看，光有“机密性”而没有“防重放鉴别”和“可用性”，照样倾家荡产！
    • 7-12（三种场景对号入座）：
      1. 既要保密、又要鉴别（验证是谁发的且不许别人看）：军事作战指令、网上银行转账、公司机密合同签署；
      2. 只要保密、不需要鉴别（不想让外人看懂内容，但不在乎验证发送者身份）：匿名举报信加密投递、自己加密存放在网盘里的私人日记、加密传输无需验证来源的公开测试流；
      3. 不需要保密、但必须严格鉴别（内容巴不得全天下都看见，但绝不允许任何人冒名顶替或篡改一个字）：政府发布的公开红头文件公告、软件官网发布的开源安装包数字签名、路由协议（如 OSPF/BGP）广播的路由更新报文！
    • 【严谨考场结论】：
    • 7-03：网络安全除机密性外，还必须包括完整性（防篡改）、端点鉴别（防假冒）、不可否认性（抗抵赖）和可用性（防 DoS）。例如：攻击者截获加密的银行转账密文后不经解密直接进行重放攻击（Replay），或发动 拒绝服务攻击（DoS） 瘫痪网络，仅靠机密性均无法防御。
    • 7-12：(1) 既需保密又需鉴别：网上银行转账交易报文、军事机密命令；(2) 需保密但不需鉴别：用户将个人本地文件加密存储或匿名加密反馈；(3) 不需保密但需鉴别：公开的新闻公告、CA 发布的数字证书与公钥、OSPF 路由器洪泛的链路状态通告（内容公开，但严禁被黑客伪造篡改）。

    19. 7-16 结合第 5 章图 5-6 计算 UDP 检验和的例子，说明为什么这种检验和不能用来鉴别报文？

    • 【故事时间 / 说人话】： UDP 的检验和就像在快递纸箱外面贴了一张普通透明胶带，上面用圆珠笔写着：“本箱重 5 斤”。如果是路途颠簸不小心掉了一块砖头（随机比特误码），收件人一称发现只有 4 斤，能发现问题。 但如果半路遇到的是个蓄意篡改的黑客呢？黑客把箱子里的真古董偷走，塞进一块一模一样重量的烂砖头，或者干脆把古董换成废纸后，自己拿圆珠笔把纸箱上的重量改写成“本箱重 1 斤”（按公开的二进制反码求和公式花 1 微秒重新算一个新的 UDP 检验和填进去）！因为算 UDP 检验和根本不需要任何秘密钥匙（密钥），黑客算得比你还溜，收件人一核对新检验和完全正确，根本发现不了报文早被掉包了！
    • 【严谨考场结论】：因为 UDP 检验和的计算算法（16 位二进制反码求和）是完全公开的，且不包含任何只有收发双方才知道的秘密信息（密钥）。入侵者截获并恶意篡改报文内容后，可以极其轻易地按照公开算法重新计算出一个与篡改后报文相匹配的新检验和并替换原检验和，接收方检验时根本无法察觉报文已被篡改或伪造。要实现报文鉴别，必须使用带密钥的报文鉴别码（MAC / HMAC）或私钥数字签名。

    20. 7-21 & 7-26 & 7-27 三大经典安全协议故事会：Kerberos、TLS 抓骗子与 PGP 邮件加密

    • (1) 7-21：试讨论 Kerberos 协议的优缺点。
    • (2) 7-26：在图 7-21（TLS 电子商务交易）中，假定第一步顾客 A 误把报文发给了一个骗子，骗子冒充经销商 B 继续下面步骤。问交互到第几个步骤时，顾客 A 可以发现对方是骗子？
    • (3) 7-27：电子邮件安全协议 PGP 主要包含哪些措施？
    • 【故事时间 / 说人话】：
    • 7-21（Kerberos 游乐园双票制）：去迪士尼乐园（大型内网），你先在检票大门（鉴别服务器 AS）验明正身，换取一张全天有效的“入园手环（TGT 票据授予票）”；然后你想玩过山车或旋转木马（各个应用服务器）时，拿手环去园内服务台（票据授予服务器 TGS）换取“过山车一次性体验券（会话密钥票据）”。
      • 好处：你的真实密码永远只在大门验证一次，绝不在网上明文传输，而且全靠飞快的对称加密！
      • 坏处：①全园所有人都指望大门和服务台（KDC），一旦它俩宕机或被黑，全网瘫痪（单点故障）；②每张票都严格印着“14:00~14:05有效”（时间戳防重放），要求全网所有电脑的时钟必须高度同步！
    • 7-26（TLS 握手第几步抓骗子？—— 看骗子有多狡猾！）： 顾客 A 在第 1 步向骗子打招呼，骗子在第 2 步必须向顾客 A 出示“经销商 B 的 CA 营业执照（数字证书）”。这时候分两种情况：
      • 情况一（笨骗子自己伪造假证书）：在 第 2 步 骗子发来假证书时，顾客 A 拿浏览器内置的 CA 公钥一验签当场报错，立刻在第 2 步就识破骗子！
      • 情况二（高明骗子去真经销商 B 网站上把 B 公开的真证书复制过来发给 A）：因为证书是公开的，A 在第 2 步验签发现证书居然是真的！于是 A 在 第 3 步 产生一个随机密码（预主密钥），用证书里 真经销商 B 的公钥加密 后发给骗子。这下骗子彻底傻眼了——因为骗子手里没有真经销商 B 的私钥，根本解不开这个加密包，在 第 4 步 骗子无法算出正确的会话密钥发回确认，顾客 A 在 第 3～4 步 彻底识破骗子！
    • 7-27（PGP 邮件的“五合一豪華套餐”）：写一封既防偷看、又防篡改、还能防赖账的 PGP 安全邮件，一共做五件事：①先对信件算个 Hash 摘要；②用发件人自己的私钥对摘要签名（防抵赖+防篡改）；③把信和签名拼在一起，临时摇号生成一个一次性对称密钥把它俩快速加密（保密）；④用收件人的公钥把这个一次性对称密钥锁起来附在信头；⑤最后用 base64 转成纯 ASCII 码发走！
    • 【严谨考场结论】：
    • 7-21（Kerberos 优缺点）：优点：基于高速对称密码体制，口令不在网上传输，通过 AS 与 TGS 双重票据实现单点登录与双向实体鉴别，使用时间戳有效防止重放攻击；缺点：①KDC（AS+TGS）存在单点故障与性能瓶颈；②严格依赖全网主机的时钟同步；③在大规模跨机构互联网中扩展性不如公钥 PKI 体系。
    • 7-26（TLS 识破骗子步骤）：若骗子发送的是伪造证书，顾客在 第 2 步 用 CA 公钥验证证书签名时即可立即发现；若骗子截获并重放了真正经销商 B 的合法数字证书，骗子虽能混过第 2 步，但在 第 3 步 顾客用真经销商 B 的公钥加密发送随机密钥后，骗子因没有 B 的私钥而无法解密获取该会话密钥，在随后的 第 4 步 无法完成加密握手验证而暴露！
    • 7-27（PGP 核心措施）：采用“密码散列函数（MD5/SHA） + 公钥密码（RSA） + 对称密码（IDEA/AES） + base64 编码”的混合加密签名体系：用发送方私钥对报文 Hash 摘要进行数字签名（提供鉴别与完整性）；用临时生成的一次性对称会话密钥加密邮件全文（提供高速机密性）；再用接收方公钥加密该一次性对称密钥随信发送。

    第八章 互联网上的音频/视频服务（共 10 题：把老公路改造成多媒体高速路）

    21. 8-03 & 8-05 & 8-08 互联网多媒体改造方案（8-03）、三种流媒体类型区别（8-05）与 IP 电话连接方式（8-08）：

    • 【故事时间 / 说人话】：
    • 8-03（怎么让原本只运煤块的公路跑救护车？）：当年互联网设计时只为了传文本邮件，根本没考虑实时视频。现在要传音视频，学术界吵出了三派方案：①“大力出奇迹派”：不用改协议，直接把光纤带宽扩宽 100 倍，路宽到永远不堵车就行了！②“应用层自己想办法派”：不动路由器，在接收端加个播放蓄水池（缓存）消除抖动，再在全国各省建分仓库（CDN 内容分发网络）就近发货；③“大改路由器派”：给路由器装上 VIP 识别器（IntServ / DiffServ），见到音视频救护车直接插队放行！
    • 8-05（看 B 站录播 vs 看世界杯直播 vs 微信视频聊天）：
      1. 流式存储音视频（看 B 站已上传电影）：文件早就录好存在服务器硬盘里了，边下边播，你可以随便拖进度条快进、暂停，开头多缓冲 5 秒钟完全无所谓；
      2. 流式实况音视频（看春晚/球赛直播）：节目正在现场边录边发，你不能往未来快进，但依然是单向看，晚个 3～5 秒看到进球也能接受；
      3. 交互式音视频（打微信语音/腾讯会议）：双向实时你一句我一句！时延一旦超过 \(0.2 \sim 0.4\text{ s}\) 双方就会互相抢话，对端到端时延要求苛刻到了极致！
    • 8-08（IP 电话的狭义广义与三种接法）：狭义就是打电话传声音；广义包括视频通话、多人电视会议、甚至即时通信（QQ/微信）。接法无非三种：两头都是电脑（PC 到 PC）、两头都是传统座机但中间借道互联网（电话到电话，两头加电话网关）、一头电脑一头座机（PC 到电话）。
    • 【严谨考场结论】：
    • 8-03（三种改造方案）：①大量增加网络链路带宽（扩容）；②不改动网络层，在应用层采用播放缓存、前向纠错与内容分发网络（CDN）自适应机制；③改造路由器体系结构，引入服务质量 QoS 机制（如综合服务 IntServ 与区分服务 DiffServ）。
    • 8-05（三类多媒体区别）：①流式存储（节目已预先录制存储在服务器上，支持暂停/快进/快退，允许几秒的初始播放缓存时延）；②流式实况（边录制边发送的实时广播/直播，不可快进，仍允许几秒的播放时延）；③交互式音视频（用户间实时双向交互通信，对端到端总时延极其敏感，通常要求严控在 \(150 \sim 400\text{ ms}\) 以内）。
    • 8-08（IP 电话）：狭义 IP 电话指在 IP 网络上打语音电话；广义 IP 电话还包括交互式多媒体实时通信（视频通话、视频会议、即时通信 IM）。三种连接方式：①两个 PC 之间通话；②两个传统固定/移动电话通过两个电话网关经由 IP 网络通话；③PC 与传统电话通过一个电话网关通话。

    22. 8-10 & 8-11 & 8-16 & 8-35 RTP 与 RTCP 协议的四个灵魂拷问：

    • (1) 8-10：为什么 RTP 协议同时具有运输层和应用层的特点？
    • (2) 8-11：RTP 协议能否提供应用分组的可靠传输？
    • (3) 8-16：话音采样率 \(8000\text{ Hz}\)，每 \(10\text{ ms}\) 装配一个分组加时间戳。时钟计数器间隔 \(\Delta\) 能否取为 \(9\text{ ms}\)？若不行应取多少？
    • (4) 8-35：一个 RTP 会话有 4 个用户多播通信，每用户发视频速率 \(100\text{ kbit/s}\)。(1) RTCP 通信量被限制在多少？(2) 每个用户能分到多少 RTCP 带宽？
    • 【故事时间 / 说人话】：
    • 8-10 & 8-11（跨界打工人 RTP）：RTP 到底是运输层还是应用层？说它像运输层，是因为它干的是端到端拆分组装、给分组编序号、打时间戳的通用运输活儿（而且封装在 UDP 里面，像是 UDP 上面的一个运输层子层）；说它像应用层，是因为它并没有写进操作系统的内核里，而是由写音视频播放器的程序员直接作为应用程序代码库编译进去的！而且注意：RTP 自己绝对不做任何确认和重传（不提供可靠传输，8-11），它只管贴序号和时间戳，丢了就丢了！
    • 8-16（尺子的刻度不能跟步长拧巴！）：发送方每隔 \(10\text{ ms}\) 稳定发 1 个语音包（即发包时刻是 \(0, 10, 20, 30, 40\text{ ms}\dots\)）。如果给时间戳配的秒表每隔 \(\Delta = 9\text{ ms}\) 才跳一格字：
      • \(10\text{ ms}\) 发第 1 包时，秒表刚跳到 1（\(9\text{ ms}\)）；
      • \(80\text{ ms}\) 发第 8 包时，秒表跳到 8（\(72\text{ ms}\)）；
      • \(90\text{ ms}\) 发第 9 包时，秒表突然跳到了 10（\(90\text{ ms}\)）！ 明明你是每隔 \(10\text{ ms}\) 均匀发包的，就因为秒表刻度 \(9\text{ ms}\) 不能整除 \(10\text{ ms}\)，打出来的时间戳差值一会儿是 1、一会儿变成 2，秒表自己凭空制造出了“假抖动”！所以标准规定：RTP 时间戳的时钟刻度 \(\Delta\) 直接取语音采样的周期——每秒采样 \(8000\) 次，每次间隔 \(\Delta = \frac{1}{8000}\text{ s} = 125\ \mu\text{s} = 0.125\text{ ms}\)（每 \(10\text{ ms}\) 包正好包含 \(80\) 个采样刻度）！
    • 8-35（RTCP 的 5% 封顶规矩）：RTCP 是用来汇报路况的控制报文，绝不能让汇报路况的车把正经拉货的车（RTP）给挤死，所以规定 RTCP 总流量不得超过会话总带宽的 \(5\%\)！4 个人每人发 \(100\text{ kbit/s}\)，总视频流量就是 \(400\text{ kbit/s}\)，那 RTCP 总共最多只能用 \(400 \times 5\% = \mathbf{20\text{ kbit/s}}\)，4 个人平摊下来每人分到 \(5\text{ kbit/s}\)！
    • 【严谨考场结论】：
    • 8-10：具有运输层特点是因为它提供端到端的实时数据传输服务（包含序号、时间戳、多路复用等运输层功能，可视为 UDP 之上的运输层子层）；具有应用层特点是因为 RTP 通常不作为操作系统内核的一部分实现，而是与具体音视频编码格式紧密结合、直接集成在应用层媒体播放软件中由开发者实现。
    • 8-11：不能！ RTP 封装在无连接的 UDP 之上，自身只提供序号和时间戳供接收端检测丢包和还原播放时序，没有任何确认（ACK）、重传、流量控制或拥塞控制机制，故不提供可靠传输。
    • 8-16：不能将 \(\Delta\) 取为 \(9\text{ ms}\)！ 因为发包间隔 \(10\text{ ms}\) 不是 \(9\text{ ms}\) 的整数倍，会导致等时发出的分组被打上差值不均匀的时间戳（在第9个分组处产生跳变误差），使接收端无法准确还原等时播放间隔。\(\Delta\) 应当取为 1 个采样周期，即 \(\Delta = \frac{1}{8000\text{ Hz}} = \mathbf{125\ \mu\text{s}}\)（\(0.125\text{ ms}\)）（或能整除 \(10\text{ ms}\) 的时间单位）。
    • 8-35 计算结果：
      • (1) 4 个用户的 RTP 总数据率为 \(4 \times 100\text{ kbit/s} = 400\text{ kbit/s}\)。按 RTCP 通信量限制占约 \(5\%\) 计算，RTCP 总通信量被限制在 \(400 \times 5\% = \mathbf{20\text{ kbit/s}}\)（若按总会话流量 \(95\%\) 为 RTP、\(5\%\) 为 RTCP 严格比例算则为 \(\frac{400}{0.95} \times 0.05 \approx \mathbf{21.05\text{ kbit/s}}\)，两种写法均给满分）；
      • (2) 4 个用户平均分配，每个用户分配到的 RTCP 带宽为 \(20 / 4 = \mathbf{5\text{ kbit/s}}\)（或 \(21.05 / 4 \approx \mathbf{5.26\text{ kbit/s}}\)）。

    23. 8-17 & 8-18 & 8-19 播放缓存空间上限（8-17）与服务质量 QoS 三大交警手段（8-18, 8-19）：

    • 【故事时间 / 说人话】：
    • 8-17（蓄水池要修多大才不会溢出来？）：接收端的播放缓存是为了吞掉网络上的“时延抖动”。如果网络最顺畅时分组 10ms 就到，最堵时要晚到 \(\Delta D_{\max}\) 秒（最大时延抖动），而这期间水龙头还在以每秒 \(R\) 比特的速率往池子里灌水，那池子至少得修多大？当然是由 数据率 \(R\) 和最大时延抖动 \(\Delta D_{\max}\) 的乘积 决定！数据率越高、抖动越大，需要的缓存空间上限就越大！
    • 8-18 & 8-19（为什么说传统互联网“毫无服务质量可言”？怎么管？）：传统 IP 协议讲究“众生平等、尽最大努力交付”——不管你是救命的远程手术视频包，还是无关紧要的垃圾邮件包，到了路由器面前统统排在一个 FIFO 队里，满了就一视同仁往地上扔，所以传统 IP 互联网根本提供不了任何时延和带宽保证（无 QoS 可言）。 要想有 QoS，路由器必须学会当交警，使出三大招（8-19）：
      1. 呼叫接纳（Call Admission）：上高速前先审查——“我这条高速路只剩 2M 带宽了，你这个视频通话开口就要 5M，对不起，直接拒绝你上路！”
      2. 管制（Policing，如漏桶算法）：上路后拿测速仪盯着你——“你买票时说平均每秒发 1M，现在突然飙到 10M，超标的包直接给你扣下或扔掉！”
      3. 调度（Scheduling，如 WFQ）：在收费站出口分设 VIP 车道和普通车道，按权重比例放行！
    • 【严谨考场结论】：
    • 8-17：接收端缓存空间的上限主要由实时数据流的数据率 \(R\) 和网络中的最大时延抖动（分组最大时延与最小时延之差）共同决定。实时数据流的数据率越大、网络的时延抖动越大，所需的缓存空间上限就越大（近似成正比关系）。
    • 8-18：服务质量 QoS（Quality of Service）是服务性能的总效果，决定用户对服务的满意程度（可用带宽、时延、抖动、丢包率等可预计指标描述）。说“互联网根本没有服务质量可言”是因为传统互联网的 IP 协议只提供无连接、尽最大努力交付（Best-Effort）的数据报服务，对所有分组一视同仁按 FIFO 转发，不预留任何资源，因此无法对时延、抖动和丢包率做出任何承诺与保证。
    • 8-19（QoS 三大机制含义）：
      1. 管制（Policing）：监测并限制进入网络的某个数据流的平均速率、峰值速率和突发长度（通常使用漏桶 Leaky Bucket 机制），防止违规突发流量冲垮网络；
      2. 调度（Scheduling）：路由器输出端口按照特定规则（如 FQ 公平排队、WFQ 加权公平排队）决定从哪个分类队列中取出下一个分组发送，以保证不同业务流的带宽份额与时延上限；
      3. 呼叫接纳（Call Admission）：在数据流开始传输前，要求应用先声明其所需的带宽和 QoS 指标；网络根据当前剩余可用资源判断是否接纳该呼叫（若剩余资源不足以保证其 QoS 且会影响现有流，则拒绝接纳）。

    第九章 无线网络和移动网络（共 6 题：看不见的空中网线与 Wi-Fi 身份证）

    24. 9-01 & 9-02 无线局域网由哪几部分组成？接入点 AP 是否就是固定基础设施（9-01）？Wi-Fi 与 WLAN 是否为同义词（9-02）？

    • 【故事时间 / 说人话】：
    • 9-01（无线网的积木是怎么搭起来的？）：你手机连上寝室墙上的无线路由器（准确学名叫接入点 AP，Access Point），你和室友的手机加上这台 AP，就组成了一个最小的无线圈子，叫基本服务集 BSS（Basic Service Set）。 那在教学楼里，一楼有个 AP1，二楼有个 AP2，怎么让你从一楼走到二楼时微信不断网呢？学校用墙里的有线网线（叫分配系统 DS，Distribution System）把一楼 AP1 和二楼 AP2 串起来，合体成一个更大的无线覆盖区，叫扩展服务集 ESS（Extended Service Set）！ 注意一个文字小陷阱：AP 只是固定基础设施的一部分（排头兵），整个固定基础设施不仅包括 AP，还包括背后连接各个 AP 和有线网的分配系统 DS！
    • 9-02（Wi-Fi 其实就是个商业商标！）：严格来说，无线局域网的技术学名叫 WLAN（Wireless LAN），它背后遵循的国际技术标准叫 IEEE 802.11。但当年向老百姓推销路由器时，要是印上“本机支持 IEEE 802.11b 标准”，谁看得懂啊！于是几家大厂商成立了一个商业认证联盟，起了一个像音响 Hi-Fi 一样朗朗上口的商标名字叫 Wi-Fi（贴上 Wi-Fi 标志就代表通过了 802.11 兼容性测试）。现在日常口语里大家早就把 Wi-Fi 当成了 802.11 无线局域网 WLAN 的同义词！
    • 【严谨考场结论】：
    • 9-01：有固定基础设施的无线局域网（WLAN）主要由 移动站（主机）、接入点 AP（Access Point，基站）、基本服务集 BSS、分配系统 DS 以及扩展服务集 ESS 组成。固定基础设施能够将无线局域网与有线互联网高速连接，并支持移动站在不同 BSS 之间漫游切换，大幅提升覆盖范围与通信性能。接入点 AP 属于固定基础设施中的核心无线接入设备，但固定基础设施不仅包含 AP，还包含后台的分配系统 DS 等有线交换网络。
    • 9-02：从严格技术定义上讲不是完全等同的同义词——WLAN（无线局域网）是技术大类名称，而 Wi-Fi 本质上是 Wi-Fi 联盟（WFA）为符合 IEEE 802.11 标准的无线局域网产品所制定的商业互操作性认证商标。但在当今实际应用与日常习惯中，人们已普遍将 Wi-Fi 与采用 802.11 标准的无线局域网 WLAN 当作同义词使用。

    25. 9-03 & 9-04 & 9-18 Wi-Fi 的“名字”与“身份证号”：SSID、BSSID、ESSID 有何区别（9-03）？关联的作用是什么（9-04）？怎么在手机电脑上查 AP 的 SSID 和 BSSID（9-18）？

    • 【故事时间 / 说人话】： 这三道题放在一起读，10 秒钟彻底顿悟： 你在星巴克掏出手机连 Wi-Fi，屏幕上搜出来的无线网名字叫 Starbucks-Free——这个给人眼看的、最多 32 个字符的网名，就叫 SSID（服务集标识符）！ 但是，星巴克一楼天花板上有 1 台 AP，二楼天花板上也有 1 台 AP，为了让顾客从一楼走到二楼不用重新输密码，店长把这两台 AP 的网名（SSID）全都设成了同一个名字 Starbucks-Free（这种跨越多个 BSS 的统一大网名也叫 ESSID）。 那你的手机网卡在空中发数据帧时，怎么区分自己到底是把帧发给一楼那台 AP 还是二楼那台 AP 呢？靠每台 AP 机器出厂固化在无线网卡里的 48 位硬件 MAC 地址！这个 AP 的 48 位 MAC 地址，就叫 BSSID（基本服务集标识符）！ 所以：SSID 是给人类看的“网名”（文字字符串，多台 AP 可以同名）；BSSID 是给网卡看的“AP 的 48 位 MAC 身份证号”（全球唯一，十六进制）！ 当你点击某个 SSID 输入密码连上去时，你的手机就和这台特定的 AP 签了一份“绑定协议”，叫关联（Association，9-04）——告诉全网：“从现在起，找我的包裹请统一交给这台 AP 转发给我！”
    • 【严谨考场结论】：
    • 9-03（SSID vs BSSID vs ESSID）：
      1. SSID（服务集标识符）：是无线局域网供用户识别的人类可读逻辑名称（最长不超过 32 字节的字符串，由管理员任意设置，如 SEU-WLAN）；当一个扩展服务集 ESS 包含多个 AP 时，该统一的网络名称也常被称为 ESSID。
      2. BSSID（基本服务集标识符）：是该基本服务集内接入点 AP 的 48 位硬件 MAC 地址（用 6 字节十六进制表示，全球唯一，用于 802.11 MAC 帧首部寻址）。
    • 9-04（关联 Association 的作用）：移动站必须先与某个接入点 AP 建立关联，才能通过该 AP 发送和接收数据帧。关联的作用是在移动站与该 AP 之间建立一条逻辑上的无线连接通道，使分配系统（DS）知道该移动站当前位于哪个 AP 的管辖之下，从而能将发往该移动站的数据帧正确路由转发给对应的 AP。
    • 9-18（如何查看 AP 的 SSID 和 BSSID）：
      • 查看 SSID：直接打开智能手机或笔记本电脑的“WLAN / Wi-Fi 设置”列表，屏幕上扫描显示出的无线网络名称即为 SSID；
      • 查看 BSSID：在电脑命令行中输入 netsh wlan show interfaces（Windows）或按住 Option 点击 Wi-Fi 图标（macOS），或使用手机 Wi-Fi 分析仪 App 查看已连接热点的详细信息，其中显示的 AP 的 48 位物理 MAC 地址（如 a4:2b:8c:xx:xx:xx） 即为 BSSID。

    26. 9-16 试比较有线以太网 IEEE 802.3 和无线局域网 IEEE 802.11，找出它们之间的主要区别。（全书局域网收官大对比！）

    • 【故事时间 / 说人话】： 一个是插着铜线光纤、在封闭管道里跑车的 802.3 有线以太网；一个是暴露在空气中、隔墙就衰减、还有隐蔽站偷袭的 802.11 无线局域网。把它们俩拉出来排排坐，正好把第 3 章和第 9 章的所有核心考点串成一张完美对比表！
    • 【严谨考场结论（六维满分对比表）】：
    比较维度 有线以太网（IEEE 802.3） 无线局域网（IEEE 802.11）
    1. 传输媒体与误码率 双绞线、光纤等导引型媒体；外界干扰小，误码率极低 无线电波（非导引型自由空间）；信号随距离衰减快、受多径效应和障碍物干扰大，误码率高
    2. MAC 介质访问协议 CSMA/CD（载波监听多点接入 / 碰撞检测）：边发送边检测碰撞（现代交换机已全双工无碰撞） CSMA/CA（载波监听多点接入 / 碰撞避免）：无法边发边检测碰撞，采用帧间间隔（DIFS/SIFS）、随机退避冻结及可选的 RTS/CTS 预约 + NAV 虚拟载波侦听 来尽量避免碰撞
    3. 链路层是否确认 无确认、无连接：收到 CRC 错帧直接丢弃，不发链路层 ACK，靠高层 TCP 重传 必须使用停止-等待确认机制：接收方每正确收到一帧数据，必须在等待 SIFS 后立即发回 链路层 ACK 确认帧，超时未收到则链路层立即重传
    4. MAC 帧地址字段数 仅含 2 个 MAC 地址字段（目的地址 DA、源地址 SA） 包含 4 个 MAC 地址字段（常用前 3 个：地址1 接收端、地址2 发送端、地址3 辅助桥接源/目的 MAC，地址4用于自组网无线网桥）
    5. 核心中心连接设备 以太网交换机（Switch） 或集线器（Hub） 接入点 AP（Access Point，无线基站） 及后台分配系统 DS
    6. 移动性与冲突范围 站点位置固定；同一网段内所有站点都能互相听到对方（无隐蔽站） 支持站点在 BSS/ESS 内移动漫游；无线信号覆盖范围有限，存在隐蔽站问题和暴露站问题
