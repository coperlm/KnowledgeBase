### `[ ]` 1. `5-12`（UDP 重传与 IP 分片重组标识辨析）

* **【已知条件与设问】**：一个应用程序用 UDP，到了 IP 层把数据报再划分为 4 个数据报片发送出去。结果前两个数据报片丢失，后两个到达目的站。过了一段时间应用程序重传 UDP，而 IP 层仍然划分为 4 个数据报片来传送。结果这次前两个到达目的站而后两个丢失。**试问：在目的站能否将这两次传输的 4 个数据报片组装成为完整的数据报？假定目的站第一次收到的后两个数据报片仍然保存在目的站的缓存中。**
* **【分步推导与标准答案】**：
  * **结论：绝对不能组装成完整的数据报！**
  * **推导过程**：
    1. IP 层是无连接的，它根本不知道上面应用程序送下来的 UDP 数据报是“第一次发送”还是“超时重传”。
    2. 当应用程序第二次重传该 UDP 数据报并向下交给 IP 层时，IP 层会将其视为一个**全新的 IP 数据报**，并在其 IP 首部中赋予一个**全新的、不同的“标识（Identification）”字段值**。
    3. 目的主机的 IP 层在进行分片重组时，**严格依据数据报首部具有相同的“源 IP 地址、目的 IP 地址、协议号以及相同的标识（Identification）字段”**来识别属于同一个原始数据报的分片。由于第一次收到的后两片与第二次收到的前两片的**“标识”字段数值不同**，目的站会把它们当作两个不同 IP 数据报的残缺分片，最终两边都因等待超时而被丢弃，无法拼在一起！

### `[ ]` 2. `5-13`（UDP 数据报在以太网上的 IP 分片计算）

* **【已知条件与设问】**：一个 UDP 用户数据报的数据字段为 $8192\text{ B}$。在链路层要使用以太网来传送（标准以太网 $\text{MTU} = 1500\text{ B}$）。**试问应当划分为几个 IP 数据报片？说明每一个 IP 数据报片的数据字段长度和片偏移字段的值。**
* **【分步计算与标准答案】**：
  1. **计算待分片的 IP 数据报总载荷长度**：UDP 数据字段 $8192\text{ B}$ 加上 **$8\text{ B}$ 的 UDP 首部**，成为 UDP 用户数据报，总长度为 $8192 + 8 = \mathbf{8200\text{ B}}$（这 $8200\text{ B}$ 就是 IP 数据报的数据载荷部分）。
  2. **计算每个分片最大可携带的数据长度**：以太网 $\text{MTU} = 1500\text{ B}$，减去固定 $20\text{ B}$ 的 IP 首部，每个分片的数据字段最大长度为 $1500 - 20 = \mathbf{1480\text{ B}}$（恰好是 8 字节的整数倍，$1480 / 8 = 185$）。
  3. **计算分片个数与最后一片长度**：
     $$\frac{8200}{1480} = 5 \text{ 余 } 800\text{ B}$$
     故应当划分为 **$6$ 个 IP 数据报片**！前 5 个分片的数据字段长度均为 **$1480\text{ B}$**，第 6 个分片的数据字段长度为 **$800\text{ B}$**。
  4. **各分片参数汇总表**：

| 分片序号 | 数据字段长度 | 原始数据字节范围（共 0~8199） | 片偏移字段数值（$= \text{起始字节} / 8$） | MF 标志 |
| :--- | :--- | :--- | :--- | :--- |
| **第 1 片** | **$1480\text{ B}$** | $0 \sim 1479$（含 8B UDP 首部 + 1472B 数据） | $0 / 8 =$ **$0$** | $1$ |
| **第 2 片** | **$1480\text{ B}$** | $1480 \sim 2959$ | $1480 / 8 =$ **$185$** | $1$ |
| **第 3 片** | **$1480\text{ B}$** | $2960 \sim 4439$ | $2960 / 8 =$ **$370$** | $1$ |
| **第 4 片** | **$1480\text{ B}$** | $4440 \sim 5919$ | $4440 / 8 =$ **$555$** | $1$ |
| **第 5 片** | **$1480\text{ B}$** | $5920 \sim 7399$ | $5920 / 8 =$ **$740$** | $1$ |
| **第 6 片** | **$800\text{ B}$** | $7400 \sim 8199$ | $7400 / 8 =$ **$925$** | $0$ |

### `[ ]` 3. `5-19`（连续 ARQ / GBN 协议发送窗口上限 $2^n - 1$ 证明）

* **【已知条件与设问】**：**试证明：当用 $n$ 比特进行分组编号时，若接收窗口等于 $1$（即只能按序接收分组），则仅在发送窗口不超过 $2^n - 1$ 时，连续 ARQ 协议才能正确运行。窗口单位是分组。**
* **【分步证明与标准答案】**：
  1. 用 $n$ 比特进行分组编号，共有 $2^n$ 个不同的序号，范围是 $0 \sim (2^n - 1)$，序号按模 $2^n$ 循环使用。
  2. **反证法**：假设发送窗口大小取到 $W_T = 2^n$（超过 $2^n - 1$）。
     * 发送方一口气连续发送 $2^n$ 个分组，序号依次为 $0, 1, 2, \dots, 2^n - 1$。
     * 假设这 $2^n$ 个分组全部被接收方正确按序收到，接收方发回了全部确认，并且接收方的接收窗口向前滑动了 $2^n$ 个位置，此时**接收方期望收到的下一个分组序号绕回变成了新的一轮序号 $0$**。
     * **极端丢包情况**：如果接收方发回的所有确认（ACK）在返回途中**全部丢失**！发送方经过超时计时器超时后，会将当前发送窗口内的 $0 \sim (2^n - 1)$ 号旧分组**全部重传**。
     * 当重传的旧 $0$ 号分组到达接收方时，由于接收方此时正好期望接收新一轮的 $0$ 号分组，**接收方根本无法分辨这个 $0$ 号分组是“重传的旧分组”还是“新发送的下一轮分组”**，从而把旧分组误当作新分组收下，导致协议彻底出错！
  3. 当限制发送窗口 $W_T \le 2^n - 1$ 时：发送方最多连续发 $0 \sim (2^n - 2)$ 共 $2^n - 1$ 个分组。若确认全在路上到达接收方后接收方期望收到序号 $2^n - 1$（不在旧窗口 $0 \sim 2^n - 2$ 内），即使确认全丢导致发送方重传 $0 \sim (2^n - 2)$，接收方发现都不是期望的 $2^n - 1$，就能立即识别出是重复旧分组而将其丢弃。得证！

### `[ ]` 4. `5-30` & `5-31`（TCP 最大窗口吞吐量与信道利用率计算）

* **【已知条件与设问】**：
  * `5-30`：设 TCP 使用的最大窗口为 $65535\text{ B}$，而传输信道不产生差错，带宽也不受限制。若报文段的平均往返时间 $\text{RTT} = 20\text{ ms}$，**问所能得到的最大吞吐量是多少？**
  * `5-31`：通信信道带宽为 $1\text{ Gbit/s}$，端到端单程传播时延为 $\tau = 10\text{ ms}$（故 $\text{RTT} = 2\tau = 20\text{ ms}$）。TCP 的发送窗口为 $65535\text{ B}$。**试问：可能达到的最大吞吐量是多少？信道的利用率是多少？**

* **【分步计算与标准答案】**：
  * **`5-30` 计算**：
    * 发送窗口大小 $W = 65535\text{ B} = 65535 \times 8 = 524,280\text{ bit}$。
    * 在每个往返时间 $\text{RTT} = 20\text{ ms} = 0.02\text{ s}$ 内最多只能发送一个窗口的数据量，故最大吞吐量为：
      $$\text{Throughput}_{\max} = \frac{W}{\text{RTT}} = \frac{524280\text{ bit}}{0.02\text{ s}} = 26,214,000\text{ bit/s} \approx \mathbf{26.21\text{ Mbit/s}}$$
  * **`5-31` 计算**：
    * **(1) 最大吞吐量**：由于 $\text{RTT} = 2 \times 10\text{ ms} = 20\text{ ms}$（发送 $65535\text{ B}$ 在 $1\text{ Gbit/s}$ 信道上的发送时延仅 $0.524\text{ ms}$，即使计入发送时延周期为 $20.524\text{ ms}$，吞吐量为 $25.54\text{ Mbit/s}$；按标准忽略极小发送时延计），最大吞吐量同样为 **$\mathbf{26.21\text{ Mbit/s}}$**（或计入发送时延为 **$25.5\text{ Mbit/s}$**）。
    * **(2) 信道利用率**：
      $$U = \frac{\text{实际最大吞吐量}}{\text{信道带宽}} = \frac{26.214\text{ Mbit/s}}{1000\text{ Mbit/s}} = \mathbf{2.62\%}\text{（或 } 2.55\% \text{）}$$
      *(工程启示：在“高带宽、长时延”的肥管道 LFN 网络中，传统 16 位窗口 $64\text{ KB}$ 会导致信道利用率极低，因此在下题 `5-35` 中必须引入 TCP 窗口扩大选项！)*

### `[ ]` 5. `5-34`（加权平均往返时间 $\text{RTT}_S$ 连续三次递推计算）

* **【已知条件与设问】**：已知第一次测得 TCP 的往返时间 $\text{RTT}$ 是 $30\text{ ms}$。接着收到了三个确认报文段，用它们测量出的往返时间样本 $\text{RTT}$ 分别是：$26\text{ ms}$、$32\text{ ms}$ 和 $24\text{ ms}$。设 $\alpha = 0.1$。**试计算每一次新的加权平均往返时间值 $\text{RTT}_S$。讨论所得出的结果。**
* **【分步计算与标准答案】**：
  * 公式：初始 $\text{RTT}_{S0} = 30\text{ ms}$；递推公式 $\text{RTT}_{S\text{新}} = (1 - \alpha)\text{RTT}_{S\text{旧}} + \alpha \cdot \text{RTT}_{\text{样本}} = 0.9 \cdot \text{RTT}_{S\text{旧}} + 0.1 \cdot \text{RTT}_{\text{样本}}$。
  1. **收到第1个样本（$\text{RTT}_1 = 26\text{ ms}$）**：
     $$\text{RTT}_{S1} = 0.9 \times 30 + 0.1 \times 26 = 27 + 2.6 = \mathbf{29.6\text{ ms}}$$
  2. **收到第2个样本（$\text{RTT}_2 = 32\text{ ms}$）**：
     $$\text{RTT}_{S2} = 0.9 \times 29.6 + 0.1 \times 32 = 26.64 + 3.2 = \mathbf{29.84\text{ ms}}$$
  3. **收到第3个样本（$\text{RTT}_3 = 24\text{ ms}$）**：
     $$\text{RTT}_{S3} = 0.9 \times 29.84 + 0.1 \times 24 = 26.856 + 2.4 = \mathbf{29.256\text{ ms}}\text{（或 } \mathbf{29.26\text{ ms}}\text{）}$$
  * **讨论结论**：虽然单次测量的 $\text{RTT}$ 样本值在 $24\text{ ms} \sim 32\text{ ms}$ 之间有较大波动，但通过取较小的权值 $\alpha = 0.1$，计算出的平滑往返时间 $\text{RTT}_S$ 始终稳定在 $29.26 \sim 30\text{ ms}$ 之间，变化非常平缓，有效滤除了网络瞬时抖动的干扰。

### `[ ]` 6. `5-35`（慢开始传送大文件的 RTT 轮次、有效吞吐率与利用率综合计算）

* **【已知条件与设问】**：用 TCP 通过速率为 $1\text{ Gbit/s}$ 的链路传送一个 $10\text{ MB}$ 的文件（注：谢书本题中窗口、分组和文件大小均采用二进制单位，即 $1\text{ MB} = 1024\text{ KB}$，$10\text{ MB} = \mathbf{10240\text{ KB}}$）。链路的往返时间 $\text{RTT} = 50\text{ ms} = 0.05\text{ s}$。TCP 选用了窗口扩大选项。在接收端，TCP 的接收窗口为 $1\text{ MB} = 1024\text{ KB}$（保持不变），发送端采用拥塞控制算法从慢开始传送。假定拥塞窗口以分组为单位计算，一开始发送 $1$ 个分组，每个分组长度都是 $1\text{ KB}$（故 $10\text{ MB}$ 文件共需发送 **$10240$ 个分组**，接收窗口上限为 **$1024$ 个分组**）。假定网络不会发生拥塞和丢包，发送端发送速率足够快（忽略发送时延），接收端每次收完一批分组后立即发确认 ACK。
  * **(1) 经过多少个 RTT 后，发送窗口大小达到 $1\text{ MB}$（即 $1024$ 个分组）？**
  * **(2) 发送端把整个 $10\text{ MB}$ 文件传送成功（发完并收到所有确认）共需要经过多少个 RTT？TCP 扩大的窗口够用吗？**
  * **(3) 根据整个文件发送成功所花费的时间（包括收到所有的确认，注：若加上三次握手建连还需额外加 $1\text{ RTT}$，此处按数据传送阶段及含建连两种口径给出），计算此传输链路的有效吞吐率和链路带宽利用率。**

* **【分步计算与标准答案（对齐教材附录A官方解答）】**：
  * **(1) 发送窗口达到 $1\text{ MB}$（$1024\text{ KB}$）所需的 RTT 数**：
    * 初始第1轮（开始时）发送窗口 $W_1 = 1\text{ KB} = 2^0\text{ KB}$；
    * 每经过 $1$ 个 $\text{RTT}$，慢开始使窗口加倍：经过 $k$ 个 $\text{RTT}$ 后，窗口大小为 $2^k\text{ KB}$。
    * 令 $2^k = 1024 \Rightarrow k = \mathbf{10\text{ 个 RTT}}$！
    * *(验证：第1~10个 RTT 内发送的分组数依次为 $1, 2, 4, 8, 16, 32, 64, 128, 256, 512$，经过第10个 RTT 收到确认后，在第11个 RTT 开始时发送窗口达到 $1024\text{ KB} = 1\text{ MB}$)*。
  * **(2) 传完整个 $10\text{ MB}$（$10240$ 个分组）并收到全部确认所需的总 RTT 数**：
    * 在前 $10$ 个 $\text{RTT}$ 内，总共已发送并确认的分组数为：
      $$1 + 2 + 4 + \dots + 512 = 2^{10} - 1 = \mathbf{1023\text{ 个分组}}\text{（即 } 1023\text{ KB）}$$
    * 从第 11 个 $\text{RTT}$ 起，受接收窗口 $\text{rwnd} = 1\text{ MB} = 1024\text{ KB}$ 的限制，发送窗口固定保持在最大值 **$1024\text{ 个分组}$** 不再增大。
    * 此时还剩余待发送的分组数 $= 10240 - 1023 = \mathbf{9217\text{ 个分组}}$。
    * 每个 $\text{RTT}$ 最多发 $1024$ 个分组：
      $$\frac{9217}{1024} = 9 \text{ 余 } 1\text{ 个分组}$$
      即还需要 **$9$ 个满载的 RTT**（发完 $9 \times 1024 = 9216$ 个分组）加上 **最后 $1$ 个 RTT**（发送最后剩下的 $1$ 个分组并收到其确认），共需 $9 + 1 = 10$ 个 $\text{RTT}$。
    * 因此，数据传送阶段共需经过 $10 + 10 = \mathbf{20\text{ 个 RTT}}$（耗时 $20 \times 50\text{ ms} = \mathbf{1.0\text{ s}}$；若计入建立 TCP 连接的 $1\text{ RTT}$ 则为 $21\text{ 个 RTT} = 1.05\text{ s}$）。
    * **窗口扩大选项够用吗？** TCP 窗口扩大选项最大可将 16 位窗口左移 14 位，即扩大到 $65535 \times 2^{14}\text{ B} \approx 1\text{ GB}$，远大于本题所需的 $1\text{ MB}$，**完全够用**！
  * **(3) 有效吞吐率与链路带宽利用率**：
    * 传送并确认完 $10\text{ MB}$ 文件总耗时 $T = 20 \times 0.05\text{ s} = 1\text{ s}$。
    * **有效吞吐率**：
      $$\text{Throughput} = \frac{10\text{ MB} \times 8\text{ bit/B}}{1\text{ s}} = 80\text{ Mbit/s}\text{（若按 } 10 \times 2^{20} \times 8\text{ bit 算则为 } \mathbf{83.89\text{ Mbit/s}}\text{）}$$
    * **链路带宽利用率**：
      $$U = \frac{83.89\text{ Mbit/s}}{1000\text{ Mbit/s}} \approx \mathbf{8.39\%}\text{（按十进制算则为 } \mathbf{8\%}\text{）}$$

### `[ ]` 7. `5-41`（TCP 连接建立、512B 数据分段传输与连接释放全流程序号推导）

* **【已知条件与设问】**：用 TCP 传送 $512\text{ B}$ 的数据。设窗口为 $100\text{ B}$，而 TCP 报文段每次也是传送 $100\text{ B}$ 的数据。再设发送方（A）和接收方（B）的起始序号分别选为 $100$ 和 $200$，**试画出类似于图 5-28 的工作示意图，从连接建立阶段到连接释放都要画上（可不考虑传播时延）。**
* **【分步序号演进表（考场画图/填空直接照抄此表）】**：
  * **关键坑点**：**三报文握手中，`SYN=1` 消耗 $1$ 个序号！** 故发送方 A 的初始 `seq = 100` 被 `SYN` 占掉后，**第 1 个数据报文段的第一个数据字节序号必须从 `101` 开始**！总共 $512\text{ B}$ 数据（字节序号为 `101 ~ 612`），每次发 $100\text{ B}$，共需分 **6 个数据报文段**（前5段各 $100\text{ B}$，第6段 $12\text{ B}$）：

| 阶段 | 报文方向 | 首部关键字段（`seq` 序号, `ack` 确认号, 标志位及数据范围） | 说明 |
| :--- | :--- | :--- | :--- |
| **一、三报文握手建连** | 1. $A \rightarrow B$ | `SYN = 1, seq = 100` | A 请求建立连接（消耗序号 100） |
| | 2. $B \rightarrow A$ | `SYN = 1, ACK = 1, seq = 200, ack = 101` | B 同意建连（消耗 B 的序号 200） |
| | 3. $A \rightarrow B$ | `ACK = 1, seq = 101, ack = 201` | A 对 B 的 SYN 确认，连接建立！ |
| **二、传送 512B 数据**<br>（窗口=100B，停等式发6段） | 4. $A \rightarrow B$ | `seq = 101, ack = 201`（携带第1段 100B：字节 `101~200`） | B 收到后回：`ack = 201` |
| | 5. $A \rightarrow B$ | `seq = 201, ack = 201`（携带第2段 100B：字节 `201~300`） | B 收到后回：`ack = 301` |
| | 6. $A \rightarrow B$ | `seq = 301, ack = 201`（携带第3段 100B：字节 `301~400`） | B 收到后回：`ack = 401` |
| | 7. $A \rightarrow B$ | `seq = 401, ack = 201`（携带第4段 100B：字节 `401~500`） | B 收到后回：`ack = 501` |
| | 8. $A \rightarrow B$ | `seq = 501, ack = 201`（携带第5段 100B：字节 `501~600`） | B 收到后回：`ack = 601` |
| | 9. $A \rightarrow B$ | `seq = 601, ack = 201`（携带第6段 12B：字节 `601~612`） | B 收到后回：**`ack = 613`** |
| **三、四报文挥手释连** | 10. $A \rightarrow B$ | `FIN = 1, ACK = 1, seq = 613, ack = 201` | A 发起释放（`FIN` 消耗序号 613） |
| | 11. $B \rightarrow A$ | `ACK = 1, seq = 201, ack = 614` | B 确认 A 的关闭请求 |
| | 12. $B \rightarrow A$ | `FIN = 1, ACK = 1, seq = 201, ack = 614` | B 也发起释放（消耗 B 的序号 201） |

### `[ ]` 8. `5-49`（十六进制 UDP 首部拆解巩固练）

### `[ ]` 9. `5-54` & `5-55` & `5-56`（16B 短数据在 UDP、IP 与以太网层的传输效率三连算）

* **【已知条件与设问】**：某客户使用 UDP 将数据发送给一个服务器，应用层数据共 $16\text{ B}$。假定 IP 首部无选项（$20\text{ B}$）。**试分别计算：(1) `5-54` 在运输层的传输效率（有用字节与总字节之比）；(2) `5-55` 在 IP 层的传输效率；(3) `5-56` 在数据链路层（使用以太网）的传输效率。**
* **【分步计算与标准答案（注意以太网最短 46B 数据填充坑点！）】**：
  1. **`5-54` 运输层传输效率**：加上 $8\text{ B}$ UDP 首部后总长为 $16 + 8 = 24\text{ B}$：
     $$\eta_{\text{运输层}} = \frac{16}{16 + 8} = \frac{16}{24} \approx \mathbf{66.7\%}$$
  2. **`5-55` IP 层传输效率**：再加上 $20\text{ B}$ IP 首部后，IP 数据报总长为 $24 + 20 = 44\text{ B}$：
     $$\eta_{\text{IP层}} = \frac{16}{16 + 8 + 20} = \frac{16}{44} \approx \mathbf{36.4\%}$$
  3. **`5-56` 以太网数据链路层传输效率（防坑必看！）**：
     * 以太网规定 MAC 帧的数据部分**最短必须为 $46\text{ B}$**（以保证最短帧长 $64\text{ B}$）！而上面交下来的 IP 数据报只有 $44\text{ B} < 46\text{ B}$，因此数据链路层**必须在后面填充 $2\text{ B}$ 的全0填充字段**，使其凑满 $46\text{ B}$。

     * 故在数据链路层的传输效率为：
       $$\eta_{\text{链路层}} = \frac{16}{46 + 18} = \frac{16}{64} = \mathbf{25\%}\text{（若计入8B前同步码则为 } \frac{16}{72} \approx 22.2\%\text{）}$$

  * `5-59`：TCP 连接使用 $1000\text{ B}$ 的窗口值，而上一次的确认号是 $22001$。现在收到了一个报文段，确认号是 $22401$。**试用图来说明在这之前与之后的窗口情况。**

  * **`5-60`（收到 `ack = 22401` 的同时，窗口值增大为 $1200\text{ B}$）**：
    * **收到之前**：窗口覆盖范围仍为 **`[22001, 23000]`**（长 $1000\text{ B}$）；
    * **收到之后**：窗口后沿向前移动 $400\text{ B}$ 到达字节 **$22401$**；而由于新窗口大小变为 $1200\text{ B}$，窗口前沿向前移动 $400 + 200 = 600\text{ B}$，到达字节 $22401 + 1200 - 1 =$ **$23600$**（即新窗口覆盖范围为 **`[22401, 23600]`**）。

### `[ ]` 11. `5-62`（TCP 连接释放状态变迁分析 —— `2025-选19` 真题同源题！）

* **【已知条件与设问】**：TCP 连接处于 `ESTABLISHED`（已建立）状态。以下的事件相继发生：(1) 收到一个 `FIN` 报文段；(2) 应用程序发送“关闭”报文。**在每一个事件之后，连接的状态是什么？在每一个事件之后发生的动作是什么？**
* **【分步状态变迁与标准答案】**：
  1. **事件 (1) 收到对端发来的 `FIN` 报文段（本端为被动关闭方）**：
     * **发生的动作**：本端 TCP 立即向对方发回一个 **`ACK` 确认报文段**（确认号为对方 `FIN` 的序号加 1），并通知本端应用程序对方已请求关闭。
     * **变迁后的状态**：从 `ESTABLISHED` 状态变迁进入 **`CLOSE-WAIT`（关闭等待）** 状态！（此时连接处于半关闭状态，本端若还有剩余数据仍可继续发送）。
  2. **事件 (2) 本端应用程序也发送“关闭”命令**：
     * **发生的动作**：本端 TCP 向对方发送一个 **`FIN`（或 `FIN + ACK`）连接释放报文段**。
     * **变迁后的状态**：从 `CLOSE-WAIT` 状态变迁进入 **`LAST-ACK`（最后确认）** 状态！（等待对方发回最后一个 `ACK` 后即彻底进入 `CLOSED` 状态）。

### `[ ]` 12. `5-65` & `5-66`（TCP 报文段首部序号 `seq` 与确认号 `ack` 关系辨析）

* **【已知条件与设问】**：
  * `5-65`：假定主机 A 向 B 发送一个 TCP 报文段。在这个报文段中，序号是 $50$，而数据一共有 $6\text{ B}$ 长。**试问，在这个报文段中的确认字段是否应当写入 $56$？**
  * `5-66`：主机 A 通过 TCP 连接向 B 发送一个很长的文件，因此这需要分成很多个报文段来发送。**假定某一个 TCP 报文段的序号是 $x$，那么下一个报文段的序号是否就是 $x + 1$ 呢？**

* **【分步辨析与标准答案】**：
  * **`5-65` 答案：绝对不是！**
    * **理由**：A 发给 B 的报文段中，序号 `seq = 50`（携带字节 $50 \sim 55$ 共 $6\text{ B}$）是 **A 自己发往 B 的数据流序号**（B 收到该报文段后，B 发回给 A 的确认号才会填 $50 + 6 = 56$）。而 **A 在自己发出的这个报文段首部中填写的“确认号（`ack`）”字段，代表的是 A 期望从 B 那里收到的下一个数据字节的序号**！它完全取决于此前 B 给 A 发送了多少字节的数据，与 A 自己这次发了多少字节毫无关系！
  * **`5-66` 答案：不是！**
    * **理由**：TCP 是**面向字节流**的协议，TCP 首部中的“序号”字段编的不是“报文段的个数编号”，而是**本报文段所发送的数据部分第一个字节在整个字节流中的字节序号**！如果当前报文段的序号是 $x$，且该报文段携带了 $L$ 个字节的数据，那么下一个报文段的序号应当是 **$\mathbf{x + L}$**（而不是 $x + 1$，除非当前报文段只携带了 1 个字节的数据）。

### `[ ]` 14. `6-26`（MIME base64 编码后含回车换行符的总字节数计算）

* **【已知条件与设问】**：一个二进制文件共 $3072\text{ B}$ 长。若使用 `base64` 编码，并且每发送完 $80\text{ B}$ 就插入一个回车符 `CR` 和一个换行符 `LF`（共 $2\text{ B}$），**问一共发送了多少个字节？**
* **【分步计算与标准答案】**：
  1. **计算 `base64` 编码后的纯字符字节数**：
     * `base64` 编码规则是将每 **$3\text{ B}$（$24\text{ bit}$）** 的二进制数据拆分为 **$4$ 个 $6\text{ bit}$ 组**，映射为 **$4\text{ B}$** 的 ASCII 文本字符（体积变为原来的 $\frac{4}{3}$ 倍）。
     * 故 $3072\text{ B}$ 二进制文件编码后的字节数为：
       $$3072 \times \frac{4}{3} = 1024 \times 4 = \mathbf{4096\text{ B}}$$
  2. **计算需要插入多少组 `CR + LF`（每满 $80\text{ B}$ 插 $2\text{ B}$）**：
     $$\frac{4096}{80} = 51 \text{ 行} \dots \text{余 } 16\text{ B}$$
     * 前 $51$ 整行（每行 $80\text{ B}$）每发送完一行都要插入 $1$ 个 `CR` 和 $1$ 个 `LF`（即每行附加 $2\text{ B}$），共需插入 $51 \times 2 = \mathbf{102\text{ B}}$。
     * **计算最终发送总字节数**：
       $$\text{总字节数} = 4096 + 51 \times 2 = \mathbf{4198\text{ B}}$$
     * *(注：若最后一行余下的 $16\text{ B}$ 末尾也额外加一组回车换行符，则为 $4198 + 2 = \mathbf{4200\text{ B}}$；教材附录A两个考虑均认可，答出 $4198\text{ B}$ 或 $4200\text{ B}$ 均给满分)*。

### `[ ]` 15. `6-48` & `6-49` & `6-50`（C/S 模式与两种 P2P 模式下的文件分发最短时间理论推导）

* **【已知条件与设问】**：一台服务器把一个长度为 $F$ 的大文件分发给 $N$ 个对等方。假设文件传输的瓶颈是各计算机（包括服务器）的**上传速率 $u$**（即服务器和所有对等方的上传速率均为相同的 $u$，而下载速率足够大不受限制）。**试分别计算在以下3种方式下，把文件分发到所有 $N$ 个对等方的最短时间：**
  * (1) `6-48`：使用**客户-服务器（C/S）方式**进行文件分发；
  * (2) `6-49`：采用 **P2P 文件分发方式，但规定每个对等方只能在接收完整个文件 $F$ 后**才能向其他对等方转发；
  * (3) `6-50`：采用 **P2P 文件分发方式，但可以把大文件划分为一个个非常小的数据块（Fluid 流体模型）**，一个对等方在下载完一个极小数据块后就能立即向其他对等方转发。

* **【分步推导与标准答案】**：
  1. **`6-48`（C/S 模式）**：
     * 只有 1 台服务器负责上传，它必须把长度为 $F$ 的文件向 $N$ 个客户机完整发送 $N$ 份，总发送数据量为 $N \cdot F$，而服务器上传速率为 $u$。
     * 最短分发时间：
       $$T_{\text{CS}} = \mathbf{\frac{N \cdot F}{u}}$$
  2. **`6-49`（整文件存储转发式 P2P 模式 —— 指数倍增树）**：
     * 发送 1 份完整文件耗时 $\frac{F}{u}$。
     * 第 1 轮（耗时 $\frac{F}{u}$）：服务器把完整文件传给第 1 个对等方（此时共有 $1$ 个对等方拥有文件，拥有完整文件的节点总数变为 $2^1 = 2$ 个，即服务器 + 对等方1）；
     * 第 2 轮（耗时 $\frac{F}{u}$）：服务器和对等方1同时向另外 2 个对等方上传（拥有文件的对等方达到 $1 + 2 = 3 = 2^2 - 1$ 个，含服务器共 $2^2 = 4$ 个节点）；
     * ……
     * 第 $k$ 轮结束后：总共可使 $2^k - 1$ 个对等方（连同服务器共 $2^k$ 个节点）获得完整文件。
     * 要让全部 $N$ 个对等方都收到完整文件，需满足 $2^k - 1 \ge N \Rightarrow 2^k \ge N + 1 \Rightarrow k = \lceil \log_2(N + 1) \rceil$ 轮。
     * 故最短分发时间为：
       $$T_{\text{P2P-整文件}} = \mathbf{\lceil \log_2(N + 1) \rceil \cdot \frac{F}{u}}$$
  3. **`6-50`（无限小分块流水线式 P2P 模式 —— 必做母题 `6-51` 的退化特例）**：
     * 当数据块极小时，任何一个对等方从第 $0$ 秒起只要收到一点点比特，就可以立即开启自己的上传带宽 $u$ 替服务器分担上传！因此全系统的最大总上传能力等于 $(1\text{ 台服务器} + N\text{ 个对等方})$ 的上传速率之和，但注意这里有一个物理边界：
     * 服务器至少要把文件的所有块发出去 1 遍（耗时 $\frac{F}{u}$），实际上当数据块无限小且下载带宽无限大时，服务器把每个极小块发给 1 个对等方的同时，该对等方瞬间转发给下一个对等方（流水线延迟趋于 $0$）！
     * *(注：若按母题 `6-51` 公式代入 $u_s = u, d = \infty$，得 $\max\left(\frac{F}{u},\ \frac{N \cdot F}{(N+1)u}\right) = \mathbf{\frac{F}{u}}$！也就是说，当把文件切成无穷小块、且下载速率无限制时，无论 $N$ 有多大，所有对等方几乎能在服务器发完 1 份文件的时间 **$\mathbf{\frac{F}{u}}$** 内通过流水线同步收齐整个文件！)*

### `[ ]` 16. `7-13` & `7-14`（对称密钥为何无法抗抵赖 vs 两种公钥签名鉴别流程对比）

* **【已知条件与设问】**：
  * `7-13`：A 和 B 共同持有一个只有他们二人知道的密钥（使用对称密码）。A 收到了用这个密钥加密的一份报文。**A 能否出示此报文给第三方，使 B 不能否认发送了此报文？**
  * `7-14`：**将图 7-5 所示的具有机密性的签名（先用发送方私钥签名、再用接收方公钥加密）与使用报文鉴别码（Hash 摘要签名）相比较，哪一种方法更有利于进行鉴别？**

* **【分步推导与标准答案】**：
  * **`7-13` 答案：不能！**
    * **理由**：因为对称密钥 $K_{AB}$ 是 **A 和 B 双方完全共享、地位对等的**。任何用 $K_{AB}$ 加密生成的报文，既可能是 B 加密发给 A 的，也完全可能是 **A 自己用 $K_{AB}$ 伪造加密出来栽赃给 B 的**！当 A 把该密文拿给第三方（法官）看时，B 完全可以矢口否认说“这是 A 自己用共享密钥编造的”，第三方根本无法判明真伪，故对称密码体制无法实现抗抵赖（不可否认性）。
  * **`7-14` 答案：使用报文鉴别码（密码散列函数 Hash + 签名，即图 7-7）的方法更有利于进行鉴别！**
    * **理由**：图 7-5 的方法需要对**整个长报文全文**先后进行两次耗时的公钥密码运算（一次私钥签名、一次公钥加密），大数模幂运算极慢，而且如果接收方只想验证报文真伪而不需要保密，也必须先做繁重的全文解密运算。而使用报文鉴别码（或对短小的定长 Hash 摘要进行签名）时，明文直接发送，**只需对极短的 128/160 位 Hash 摘要做一次运算**，计算速度比对全文做公钥加解密快成千上万倍！

### `[ ]` 17. `7-20`（中间人攻击 MITM 过程剖析与防御）

* **【已知条件与设问】**：**什么是“中间人攻击（Man-In-The-Middle Attack）”？怎样防止这种攻击？**
* **【分步还原与标准答案】**：
  * **攻击过程（以 A 与 B 交换公钥通信为例）**：
    1. A 想向 B 索要公钥，或者 A 把自己的公钥 $PK_A$ 发送给 B；
    2. 潜伏在链路中间的攻击者 C（中间人）截获了双方的通信：C 把**自己伪造的公钥 $PK_C$** 冒充成 B 的公钥发给 A，同时又把 $PK_C$ 冒充成 A 的公钥发给 B！
    3. 随后，A 用以为是 B 的公钥（实为 $PK_C$）加密机密数据发出去，C 截获后用自己的私钥 $SK_C$ 轻松解密偷看甚至篡改，然后再用真正的 $PK_B$ 重新加密后转发给 B。A 和 B 全程以为在跟对方直接保密通信，实际上所有内容都在中间人 C 面前“裸奔”！
  * **防御方法**：严禁直接在网络上明文裸传公钥！必须使用可信第三方 **认证中心 CA（Certification Authority）签发的数字证书（X.509）**，将实体的身份信息与其公钥绑定并用 CA 的私钥进行数字签名。通信前先用预装在浏览器/系统中的 CA 公钥验证对方证书真伪，中间人因没有 CA 私钥而无法伪造假证书。

### `[ ]` 18. `7-22` & `7-23`（网络层 IPsec 核心协议族与安全关联 SA 复用机制）

* **【已知条件与设问】**：
  * `7-22`：互联网的网络层安全协议族 IPsec 都包含哪些主要协议？
  * `7-23`：用户 A 和 B 使用 IPsec 进行通信。A 需要向 B 接连发送 6 个分组。**是否需要在每发送一个分组之前，都先建立一次安全关联 SA？**

* **【分步解析与标准答案】**：
  * **`7-22` IPsec 三大核心协议组件**：
    1. **鉴别首部协议 AH（Authentication Header，协议号 51）**：提供**源点鉴别和数据完整性**，但**不提供机密性（不加密）**；
    2. **封装安全有效载荷协议 ESP（Encapsulating Security Payload，协议号 50）**：同时提供**源点鉴别、数据完整性和机密性（加密）**（实际应用最广）；
    3. **互联网密钥交换协议 IKE（Internet Key Exchange）**：用于在通信前自动协商加密算法、鉴别算法并安全地生成和交换会话密钥，建立安全关联 SA。
  * **`7-23` 答案：不需要！**
    * **理由**：**安全关联 SA（Security Association）** 是 IPsec 中在两个通信实体之间建立的一条单向逻辑安全连接（内部保存了协商好的加密算法、共享会话密钥、安全参数索引 SPI 以及防重放的递增序号计数器）。A 向 B 发送这 6 个分组之前，**只需要通过 IKE 建立 1 次安全关联 SA**，随后的全部 6 个分组（乃至整个会话期间成千上万个分组）都直接复用这一条已建立好的 SA 进行加密和序号递增传输，绝不需要每发一个分组都建一次 SA！

### `[ ]` 19. `7-25`（运输层安全协议 TLS/SSL 握手与工作全流程）

* **【已知条件与设问】**：**试简述协议 TLS（安全运输层协议）的工作过程。**
* **【分步流程标准答案（4步握手法）】**：
  1. **第一步（协商密码套件与交换随机数）**：客户 A 向服务器 B 发送客户端版本号、支持的加密算法列表及客户端随机数 $R_1$；服务器 B 从中选定双方都支持的加密算法套件，发回服务器版本号和服务器随机数 $R_2$。
  2. **第二步（服务器发送证书与客户验证）**：服务器 B 向客户 A 发送自己的 **CA 数字证书（内含服务器公钥 $PK_B$）**；客户 A 用本地受信任的 CA 公钥验证该数字证书的真实性，从中提取出安全可靠的服务器公钥 $PK_B$。
  3. **第三步（产生并加密传递预主密钥，生成会话密钥）**：客户 A 随机产生一个保密的 **预主密钥（Premaster Secret，随机数 $R_3$）**，用刚才提取出的 **服务器公钥 $PK_B$ 将其加密** 后发送给服务器 B；服务器 B 用自己的私钥 $SK_B$ 解密得到预主密钥 $R_3$。随后，A 和 B 双方各自利用手头相同的三个随机数 $(R_1, R_2, R_3)$，使用相同的算法独立计算出本次会话所用的**对称加密会话密钥和 MAC 鉴别密钥**。
  4. **第四步（安全数据传输阶段 —— 记录协议）**：握手完成！此后双方将应用层数据（如 HTTP 报文）切块压缩，加上 **MAC（报文鉴别码）** 后，使用刚刚生成的**对称会话密钥（如 AES）进行高速加密传输**。

### `[ ]` 21. `8-20`（三种路由器分组排队调度机制对比：FIFO vs FQ vs WFQ）

* **【已知条件与设问】**：**试比较先进先出（FIFO）排队、公平排队（FQ）和加权公平排队（WFQ）的优缺点。（官方大纲六(十)3 核心考点）**
* **【对比表格标准答案】**：

| 调度策略 | 工作原理 | 主要优点 | 主要缺点 |
| :--- | :--- | :--- | :--- |
| **1. 先进先出（FIFO / FCFS）** | 所有分组进入同一个单一队列，严格按到达路由器的先后次序输出，满了就尾部丢弃。 | **实现极其简单**，路由器硬件与计算开销最小。 | **无法区分业务优先级**！高速突发的大数据流会霸占整个队列，导致对时延极其敏感的短小实时音视频分组遭受极大的排队时延甚至被丢弃。 |
| **2. 公平排队（FQ）** | 为每一类数据流设置独立的队列，按轮询（Round-Robin，严格说按**逐字节虚拟完结时间**）轮流为每个非空队列服务，使各队列平分链路带宽。 | **保证了各数据流之间的绝对公平**，防止恶意长分组流饿死短分组流。 | 所有队列获得的带宽份额完全相等，**无法为高优先级的实时多媒体业务分配比普通业务更多的带宽**。 |
| **3. 加权公平排队（WFQ）** | 为每个队列分配不同的**权重 $w_i$**，使第 $i$ 个队列能够获得至少 $\frac{w_i}{\sum w_k} \times R$ 的保证带宽，且空闲带宽按权重比例动态共享。 | **兼顾公平性与差异化服务质量（QoS）**！既可为高权重实时音视频流提供确定性的最低带宽与最大时延上限保证，又不会饿死低优先级流。 | 路由器需要维护多队列并计算虚拟完结时间，**实现复杂度与开销比 FIFO 高**。 |

### `[ ]` 22. `8-33`（IP 电话 VoIP 封装 RTP + UDP + IP 首部后的数据率与开销增长率计算）

* **【已知条件与设问】**：假定 IP 电话的发送方在讲话时，每秒钟产生 $8000\text{ B}$ 的话音数据。每隔 $20\text{ ms}$ 把得到的数据块加上 RTP 首部（固定 $12\text{ B}$）和 UDP 首部（$8\text{ B}$）后，交给 IP 层（固定首部 $20\text{ B}$）发送出去。假定 RTP 首部和 IP 首部都没有选项。**试计算发送方在发送这种 IP 数据报时的数据率（$\text{kbit/s}$）。这个数据率比原始的话音数据率增加了百分之多少？**
* **【分步计算与标准答案】**：
  1. **原始话音数据率 $R_{\text{原始}}$**：
     $$R_{\text{原始}} = 8000\text{ B/s} \times 8\text{ bit/B} = 64000\text{ bit/s} = \mathbf{64\text{ kbit/s}}$$
  2. **每个分组（每 $20\text{ ms}$）包含的字节数**：
     * 每秒切分的分组个数 $= \frac{1\text{ s}}{20\text{ ms}} = \frac{1000\text{ ms}}{20\text{ ms}} = \mathbf{50\text{ 个分组/秒}}$。
     * 每个分组内的原始话音数据块长度 $= \frac{8000\text{ B}}{50} = \mathbf{160\text{ B}}$。
     * 每个分组附加的三层协议首部总开销 $= \text{RTP}(12\text{ B}) + \text{UDP}(8\text{ B}) + \text{IP}(20\text{ B}) = \mathbf{40\text{ B}}$！
     * 故每个 IP 数据报的总长度 $= 160\text{ B} + 40\text{ B} = \mathbf{200\text{ B}}$。
  3. **发送 IP 数据报时的实际数据率 $R_{\text{IP}}$**：
     $$R_{\text{IP}} = 50\text{ 个/s} \times 200\text{ B} \times 8\text{ bit/B} = 80000\text{ bit/s} = \mathbf{80\text{ kbit/s}}$$
  4. **比原始话音数据率增加的百分比**：
     $$\text{增加比例} = \frac{80\text{ kbit/s} - 64\text{ kbit/s}}{64\text{ kbit/s}} = \frac{40\text{ B}}{160\text{ B}} = \mathbf{25\%}$$

### `[ ]` 23. `8-36`（流媒体播放器缓存抽空暂停与注满时间计算 —— 漏桶/水池进出水模型）

* **【已知条件与设问】**：在图 8-7 中，客户机的应用程序缓存容量为 $100\text{ Mbit}$。假定只要当应用程序缓存没有存满数据，TCP 接收缓存就要向应用程序缓存传送视频数据，并且**注入数据率是 $r_{\text{in}} = 2\text{ Mbit/s}$**，而播放器从应用程序缓存**读取播放数据的速率是 $r_{\text{out}} = 3\text{ Mbit/s}$**。当应用程序缓存所存储的数据**达到 $30\text{ Mbit}$ 时，播放器就开始从应用程序缓存中读取数据，开始播放视频**。
  * **(1) 播放器播放多少时间后就暂停了（无数据可读取了）？暂停多久后才能继续播放？**
  * **(2) 现在把假定条件改变一个，即把 TCP 接收缓存向应用程序缓存传送视频数据的数据率改为 $r_{\text{in}}' = 4\text{ Mbit/s}$（大于读取速率 $3\text{ Mbit/s}$）。试计算从 TCP 接收缓存向应用程序缓存传送数据开始（即从空缓存 $0\text{ Mbit}$ 开始），然后到 $30\text{ Mbit}$ 播放器开始播放视频，再到应用程序缓存满了数据（达到 $100\text{ Mbit}$）为止，总共花费多少时间？**

* **【分步计算与标准答案（经典“进水管 vs 出水管”问题，必会！）】**：
  * **(1) 当注入速率 $r_{\text{in}} = 2\text{ Mbit/s} < \text{播放速率 } r_{\text{out}} = 3\text{ Mbit/s}$ 时**：
    * **① 播放多久后暂停（缓存被抽空）**：
      * 刚开播瞬间，缓存里已有初始蓄水量 $30\text{ Mbit}$；
      * 开播期间，一边以 $2\text{ Mbit/s}$ 往里进水，一边以 $3\text{ Mbit/s}$ 往外抽水，故缓存数据的**净消耗速率**为：
        $$r_{\text{净減}} = 3\text{ Mbit/s} - 2\text{ Mbit/s} = \mathbf{1\text{ Mbit/s}}$$
      * 把已有的 $30\text{ Mbit}$ 彻底抽空所需的时间（即持续播放时间）为：
        $$t_{\text{播放}} = \frac{30\text{ Mbit}}{3 - 2\text{ Mbit/s}} = \mathbf{30\text{ s}}$$
    * **② 暂停多久后才能继续播放**：
      * 暂停期间，播放器停止读取（$r_{\text{out}} = 0$），只有 TCP 以 $2\text{ Mbit/s}$ 往缓存里注入数据；
      * 要重新攒够启动播放门槛 $30\text{ Mbit}$，需要暂停等待的时间为：
        $$t_{\text{暂停}} = \frac{30\text{ Mbit}}{2\text{ Mbit/s}} = \mathbf{15\text{ s}}$$
  * **(2) 当注入速率改为 $r_{\text{in}}' = 4\text{ Mbit/s} > \text{播放速率 } r_{\text{out}} = 3\text{ Mbit/s}$ 时（分两段相加）**：
    * **第一阶段（从 $0\text{ Mbit}$ 攒到 $30\text{ Mbit}$，此时播放器尚未开始播放）**：
      * 只有进水（$4\text{ Mbit/s}$），没有出水，攒够 $30\text{ Mbit}$ 耗时：
        $$t_1 = \frac{30\text{ Mbit}}{4\text{ Mbit/s}} = \mathbf{7.5\text{ s}}$$
    * **第二阶段（从 $30\text{ Mbit}$ 开始边播边下，直到把 $100\text{ Mbit}$ 缓存彻底灌满）**：
      * 还需继续往缓存里净增加的容量 $= 100\text{ Mbit} - 30\text{ Mbit} = \mathbf{70\text{ Mbit}}$；
      * 此时一边以 $4\text{ Mbit/s}$ 进水，一边以 $3\text{ Mbit/s}$ 播放出水，缓存数据的**净增长速率**为：
        $$r_{\text{净增}} = 4\text{ Mbit/s} - 3\text{ Mbit/s} = \mathbf{1\text{ Mbit/s}}$$
      * 灌满剩余 $70\text{ Mbit}$ 所需耗时：
        $$t_2 = \frac{100 - 30\text{ Mbit}}{4 - 3\text{ Mbit/s}} = \mathbf{70\text{ s}}$$
    * **总共花费时间**：
      $$T_{\text{总}} = t_1 + t_2 = 7.5\text{ s} + 70\text{ s} = \mathbf{77.5\text{ s}}$$

## 第九章 无线网络和移动网络（共 2 道综合应用题）

### `[ ]` 24. `9-13`（802.11 CSMA/CA 退避计时器“冻结剩余数值”机制原理分析）

* **【已知条件与设问】**：**冻结退避计时器剩余数值的做法是为了使协议对所有站点更加公平。请进一步解释。**
* **【分步解释与标准答案】**：
  1. **什么是退避计时器冻结规则**：在 802.11 的 CSMA/CA 协议中，当站点 A 抽取出随机退避时间（如 10 个时隙）并开始倒计时期间，若在倒计时还剩 4 个时隙时，检测到信道突然变忙（被另一个退避时间更短的站点 B 抢先占用了信道），站点 A **不会把退避计时器清零作废，而是立即“冻结（暂停）”剩余的 4 个时隙数值**；等站点 B 发送完毕、信道再次空闲并经过 DIFS 后，站点 A 直接**从上次冻结的剩余数值（4 个时隙）继续往下倒计时**！
  2. **为什么这样做更公平**：如果不冻结剩余数值，而是每次信道变忙都迫使落败的站点重新随机抽取一个新的退避时间，那么刚才已经苦苦等待了一大半时间的站点 A 之前付出的等待时间就彻底白费了，它可能会在与新加入竞争的站点 C 抽签时再次抽到大数而一再被插队饿死。**冻结剩余数值保证了“先开始等待的站点，在下一轮竞争中只需走完剩下的短短几步就能优先抢到信道”**，近似实现了“先来先服务”的公平性。

### `[ ]` 25. `9-15`（802.11 无线局域网 MAC 帧首部四个地址字段——重点是地址 1、2、3 填写实战）

* **【已知条件与设问】**：**试用简单的例子说明无线局域网的 MAC 帧首部中地址 3 的作用。（官方大纲三(六)3 核心考点，必须掌握地址 1、2、3 的填表规则！）**
* **【分步规则与实例标准答案】**：
  1. **先记牢 802.11 数据帧首部前三个 MAC 地址的万年铁律**：
     * **地址 1（接收端 RA）**：永远填 **无线信道上直接接收该帧的下一跳设备 MAC**；
     * **地址 2（发送端 TA）**：永远填 **无线信道上直接发出该帧的当前设备 MAC**；
     * **地址 3（辅助端到端寻址）**：用来在 AP（接入点，工作在链路层）在无线帧 `802.11` 与有线以太网帧 `802.3` 之间做帧格式转换时，**补齐真正的源 MAC 地址或最终局域网目的 MAC 地址（如路由器接口 MAC）**！

| 传输方向（含字段标志） | `To AP` (去往AP) | `From AP` (来自AP) | **地址 1（直接接收方）** | **地址 2（直接发送方）** | **地址 3（辅助桥接地址）** |
| :--- | :---: | :---: | :--- | :--- | :--- |
| **情况一：无线站 A $\rightarrow$ AP**（去往路由器 R） | `1` | `0` | **AP 的 MAC** | **无线站 A 的 MAC** | **路由器 R 接口的 MAC（最终目的）** |
| **情况二：AP $\rightarrow$ 无线站 A**（来自路由器 R） | `0` | `1` | **无线站 A 的 MAC** | **AP 的 MAC** | **路由器 R 接口的 MAC（最初源站）** |

  2. **考场答题标准例子**：
     * 设无线局域网中的站点 A 要通过接入点 AP 向连接在有线局域网上的路由器 R 发送一个数据报（或反之，路由器 R 通过有线网发帧经 AP 转给无线站 A）。
     * **若从路由器 R 发往无线站 A**：路由器 R 发出的是标准有线 `802.3` 以太网帧（里面只有两个地址：源地址 $=$ $R\text{ 的 MAC}$，目的地址 $=$ $A\text{ 的 MAC}$）。当 AP 从有线网口收到该帧并转换为 `802.11` 无线帧发给 A 时，**地址 1 填 A 的 MAC，地址 2 填 AP 自己的 MAC**——如果没有**地址 3**，A 收到无线帧后只看得到是 AP 发来的，根本不知道这个帧最初是路由器 R 发过来的！因此 AP 必须把 **路由器 R 的源 MAC 地址填入“地址 3”** 中。
     * **反之，若从无线站 A 发往路由器 R**：A 发出的无线帧中，**地址 1 填 AP 的 MAC，地址 2 填 A 自己的 MAC，地址 3 填路由器 R 的目的 MAC**。这样 AP 收到该无线帧后，才能从**地址 3** 中读出最终要把转换后的有线 `802.3` 以太网帧发给谁（路由器 R）！
