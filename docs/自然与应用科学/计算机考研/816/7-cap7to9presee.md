## 模块一：第7章 网络安全（对应 816 考纲 六(九)）

> **考纲要求**：1. 系统安全、网络安全基本原理；2. 基本加密算法适用方法与数字签名；3. 访问控制、信息加密与基本攻击原理。

### 一、 坏人是怎么搞破坏的？（攻击分类与安全目标）

想象小红（A）要给小明（B）通过快递寄一封机密商业合同，半路上有个黑客老王（E）盯着这条路。老王搞破坏的手段分为两大类：

1. **被动攻击（只偷看、不动手）**：
   * 老王不拦快递车，也不改信件内容，只是拿个透视镜偷偷看信里写了啥（**截获/窃听**）；或者就算信锁在保险箱里看不见字，老王天天蹲在路边数小红一天给小明寄几个箱子、箱子有多重，从而猜出两人是不是马上要签大合同了（这叫**流量分析 Traffic Analysis**）。
   * **防守策略**：被动攻击不会在信件上留下任何痕迹，所以**极难检测，只能靠“事前预防”（即给数据加密）**。
2. **主动攻击（直接动手脚）**：
   * **篡改（Modification）**：把合同里的“付款 100 万”涂改成“付款 1 块”；
   * **伪造/假冒（Masquerading）**：老王自己写一封信，落款冒充小红寄给小明；
   * **重放攻击（Replay Attack）**：小红给银行发了一条加密指令“给老王转账 100 元”。老王虽然解不开这个加密包，但他把这个加密包原封不动地复印了 100 份，连续往银行窗口塞了 100 次，让银行重复执行扣款！
   * **拒绝服务（DoS / DDoS）**：老王雇了一万个人把快递站大门堵死，让小红的正经信件根本寄不出去。
   * **防守策略**：主动攻击很难通过纯加密彻底预防，必须结合**加密、报文鉴别、序号/时间戳以及入侵检测系统（IDS）**来“检测并恢复”。

由此引出网络安全的三大核心目标（记住它们各自的含义界限）：
* **机密性（Confidentiality）**：不让外人看懂内容（靠**加密**解决）；
* **完整性（Integrity）与报文鉴别（Authentication）**：证明信件确实是声称的那个人写的，且路上**一个字都没被改过**（注意：光把信锁进普通箱子并不能防止别人把整个箱子掉包或重放，所以**仅有“机密性”的网络绝不等于安全**！）；
* **不可否认性（Non-repudiation，抗抵赖）**：发信人事后不能耍赖说“这封信不是我发的，是你自己伪造栽赃我的”。

### 二、 两把锁的艺术：对称密码 vs 公钥（非对称）密码

密码学里只有两大家族，把它们的脾气摸透，所有加密题都能迎刃而解：

#### 1. 对称密码体制（Symmetric Crypto，如 DES、3DES、AES）
* **工作原理**：加密和解密用的是**同一把钥匙 $K$**（双方事先在私底下悄悄配好同一把钥匙）。
* **核心优缺点**：
  * **优点**：加解密的数学运算极其简单，**速度飞快**！用来加密几百 MB 的电影或长文件毫无压力。
  * **缺点**：①**密钥分发是个噩梦**——如果有 $N$ 个人想两两保密通信，总共需要事先配好 $\frac{N(N-1)}{2}$ 把不同的钥匙；而且两人相隔万里，怎么把这把钥匙安全地寄给对方？（通常需要找一个大家都绝对信任的第三方“密钥分配中心 KDC”，最著名的协议叫 **Kerberos**）。②**无法防止内部人耍赖（无抗抵赖性）**——因为同一把钥匙只有小红和小明两个人有，如果小明自己用这把钥匙伪造了一封信，然后去法院告小红，法官根本分不清这封信到底是小红写的还是小明自己写的！

#### 2. 公钥密码体制（Public-Key / 非对称密码，如 RSA）
* **工作原理**：每个人去配锁店打造的不是一把钥匙，而是**一对在数学上死死咬合的钥匙**：
  * **公钥（Public Key, $PK$）**：相当于一把**“敞开挂在全世界门口的挂锁”**，全天下任何人都可以免费拿你的公钥把箱子咔哒一声锁上；
  * **私钥（Private Key, $SK$）**：相当于**“唯一能打开这把挂锁的钥匙”**，全宇宙只有你自己的保险柜里藏着这一把，绝对不给第二个人看！
* **两大神仙用法（考场铁律：盯紧到底用谁的公钥、谁的私钥！）**：
  1. **用法一：保密通信（不让外人看）——“用收件人的公钥加密，用收件人的私钥解密”**
     * 小红想给小明发悄悄话 $X$，小红去公开目录里拿来 **小明的公钥 $PK_B$** 把信锁上：$Y = E_{PK_B}(X)$。
     * 信在路上就算被全天下截获也没用，因为只有小明兜里有 **小明的私钥 $SK_B$**，只有小明能算出 $D_{SK_B}(Y) = X$！
  2. **用法二：数字签名（防伪造、防抵赖）——“用发件人自己的私钥签名，用发件人的公钥验证”**
     * 数学家设计 RSA 时让两个密钥具有对偶性：$E_{PK}(D_{SK}(X)) = X$。
     * 小红写了一份公开声明 $X$，她先用全天下只有她自己才有的 **小红私钥 $SK_A$** 对文件做一次运算 $S = D_{SK_A}(X)$ 发出去。
     * 收到信的任何人，只要拿公开的 **小红公钥 $PK_A$** 算一下 $E_{PK_A}(S)$，如果还原出来的刚好是可读的原文 $X$，这就铁证如山地证明了三件事：
       * **①身份鉴别**：除了小红，世上没人有 $SK_A$，这绝对是小红亲手签的；
       * **②不可否认（抗抵赖）**：小红事后在法官面前绝对赖不掉；
       * **③完整性**：如果老王在路上改了半个字，用 $PK_A$ 解出来的就会是一堆乱码！

### 三、 怎么给大文件做高速签名？（散列函数 Hash 与报文鉴别码 MAC）

刚才说的公钥算法（RSA）有个致命弱点：**大数模幂运算实在太慢了！** 如果一份文件有 $100\text{ MB}$，直接拿私钥去对整份文件做 RSA 签名，电脑要算半天。怎么加速？

#### 1. 密码散列函数（Hash Function，如 MD5、SHA-1）——“文件的指纹提取器”
* 不管你输入的文件是 1 句话还是 10 部电影（任意长度），散列函数 $H(M)$ 都能在几毫秒内算出一个**固定长度的短小的“指纹”（叫报文摘要 Message Digest，比如 MD5 固定输出 128 位，SHA-1 固定输出 160 位）**。
* 它具有三大铁律：**①单向不可逆**（拿到指纹绝不可能反推出原文件）；**②雪崩效应**（原文件哪怕只改了一个标点符号，算出来的指纹也会面目全非）；**③抗碰撞性**（绝对找不出两份不同的文件拥有相同的指纹）。

#### 2. 工业界的标准做法：先取指纹，再锁指纹！
* **高效数字签名**：小红发 $100\text{ MB}$ 的文件 $M$ 时，先花 1 毫秒算出 160 位的短指纹 $H(M)$，然后**只用自己的私钥 $SK_A$ 对这短短 160 位的指纹进行加密（签名）**，附在原文件屁股后面一起发走！这比直接签整份文件快了成千上万倍！
* **报文鉴别码（MAC）**：如果小红和小明不想用慢吞吞的公私钥，只想用共享的对称秘密串 $K$ 来防篡改，怎么办？小红把文件 $M$ 和秘密串 $K$ 拼在一起算个指纹 $H(M + K)$ 附在信后面（这个带秘密钥匙的指纹就叫**报文鉴别码 MAC**）。老王在路上没有秘密串 $K$，他要是敢改文件 $M$，就绝对算不出正确的 MAC！（对比思考：普通的 CRC 或运输层检验和因为没有掺入秘密钥匙 $K$，谁都能重算，所以只能防自然误码，绝不能防黑客篡改！）。

### 四、 三大经典攻防博弈：防重放、防中间人、跨层安全协议

#### 1. 怎么在不发密码的情况下证明“我是我”？（不重数 Nonce 与防重放）
* 如果小明问：“你是小红吗？”小红直接把双方约定的暗号发过去，老王在旁边录下音，明天老王播放这段录音就能冒充小红了（**重放攻击**）。
* **正确做法（挑战-应答机制）**：小明每次随机摇号生成一个**绝不重复使用的随机数 $R$（叫“不重数 Nonce”）**发给小红：“请用咱俩的共享密钥把今天的随机数 $R$ 加密发回来！”因为每次的 $R$ 都不一样，老王昨天录下来的密文今天就彻底作废了！
* **工程铁律**：在使用不重数进行双向鉴别时，必须严防老王“借刀杀人（把你发给他的随机数原样反弹回来让你自己替他加密）”，因此双方不能使用完全对称且允许相同随机数的格式（或加入发送方身份标识、时间戳、严格递增的序号）。

#### 2. 怎么防止坏人把公开挂锁偷梁换柱？（中间人攻击 MITM 与认证中心 CA）
* 公钥是公开的，但这带来了一个恐怖的漏洞——**中间人攻击（Man-in-the-Middle Attack）**：
  * 小红在网吧喊了一声：“小明，把你的公钥发给我！”
  * 躲在路由器里的黑客老王把小明的真公钥拦下来扔掉，把**老王自己的公钥 $PK_E$** 发给了小红，谎称“这就是小明的公钥”！
  * 小红信以为真，用老王的公钥 $PK_E$ 把机密合同锁上发出去；老王在半路用自己的私钥 $SK_E$ 轻松打开偷看甚至篡改后，再用刚才截获的小明真公钥 $PK_B$ 锁上发给小明！小红和小明聊了一整天，浑然不知中间夹了个偷听一切的老王！
* **终极克星：认证中心 CA 与数字证书（Digital Certificate）**：
  * 怎么证明这个公钥真的是小明的？去国家工商局（**认证中心 CA**）办一张防伪身份证（**数字证书**）！
  * CA 审查完小明的真实身份后，把 **“小明的名字 + 小明的公钥 $PK_B$”** 写在一张电子文件上，然后用 **CA 自己的私钥 $SK_{\text{CA}}$** 盖上防伪钢印（数字签名）！
  * 以后小明给别人发公钥时，直接发这张数字证书。小红电脑的浏览器出厂时就已经焊死了 **CA 的公钥 $PK_{\text{CA}}$**，拿 $PK_{\text{CA}}$ 一验钢印，老王的假公钥当场现原形！

#### 3. 协议栈里的“三大保镖”与防火墙
把上面的零件组装起来，放在网络的不同层次，就构成了三大实战协议：
1. **网络层保镖：`IPsec`（常用于机构间建 VPN）**：
   * 在两个路由器或主机之间建立单向的逻辑安全通道，叫 **安全关联 SA（Security Association，注意：一条 SA 只能保卫一个方向，双向通信必须建两条 SA；一旦建好一条 SA，后续成千上万个分组都直接复用这条 SA，绝不需要每发一个包建一次 SA！）**。
   * 包含两大核心子协议：**`AH`（鉴别首部：只管防篡改和鉴别，不管加密保密）** 和 **`ESP`（封装安全有效载荷：既管加密保密，又管防篡改鉴别，最常用！）**。
   * **防重放序号机制**：ESP 首部里有自己独立的**单调递增 32 位序号**。哪怕上层 TCP 因为丢包重传了同一个 TCP 报文段，到了网络层 IPsec 封装时，也**必须给它分配一个新的递增 IPsec 序号**（否则接收方 IPsec 会误以为是黑客重放的旧包而直接拒收！）。
2. **运输层保镖：`TLS / SSL`（就是你每天刷到的 `HTTPS`）**：
   * 位于 TCP 之上、应用层之下。它的握手核心思想是**“混合加密”**：
     1. 浏览器先跟服务器打招呼，服务器把自己的 **CA 数字证书（内含服务器公钥）** 发给浏览器；
     2. 浏览器用 CA 公钥验明正身后，自己随机生成一个临时密码（预主密钥），用**服务器的公钥加密**发给服务器（只有真服务器有私钥能解开！）；
     3. 双方用这个秘密派生出**对称会话密钥**，接下来的网页传输全部改用飞快的**对称加密 + MAC 完整性校验**！
3. **应用层邮件保镖：`PGP`**：
   * 把数字签名（Hash + 发件人私钥）和混合加密（一次性对称密钥加密正文 + 收件人公钥加密该对称密钥）完美打包在一起的电子邮件安全标准。
4. **大门保安：防火墙（Firewall）**：
   * **网络级防火墙（分组过滤路由器）**：工作在网络层和运输层，只看信封表面的 **源/目的 IP、源/目的端口、协议号、TCP 标志位**，速度快但看不懂信件内容；
   * **应用级防火墙（应用网关 / 代理服务器）**：工作在应用层，把信拆开逐字审查应用层内容，安全性极高但转发慢。

## 模块二：第8章 互联网上的音/视频服务与流媒体（对应 816 考纲 六(十)）

> **考纲要求**：1. 流媒体的概念；2. 流媒体应用的工作方式。

### 一、 为什么看视频最怕“时延抖动（Jitter）”？怎么用“蓄水池”治好它？

#### 1. 流媒体的脾气與时延抖动
普通下载文件要求“一个字节都不能错，哪怕晚到几秒也没事”（所以用 TCP）；而流媒体（**边下载、边播放**）恰恰相反：少一两个画面顶多闪一下，但**绝对不能卡顿或忽快忽慢**（所以实时音视频底层一律用 **UDP**，宁可丢弃太晚到达的包，也绝不重传）。

假设主播对着麦克风说话，声卡每隔恒定的 $20\text{ ms}$ 生成并发送一个语音包（这叫**等时数据 Isochronous**）。但是这些包进了互联网后，第 1 个包碰上路由器空闲，花了 $30\text{ ms}$ 就到了；第 2 个包碰上路由器排队堵车，花了 $70\text{ ms}$ 才到；第 3 个包花了 $40\text{ ms}$ 到……
* **端到端时延**：每个包各自在路上花的时间（如 $30\text{ ms}, 70\text{ ms}, 40\text{ ms}$）；
* **时延抖动（Jitter）**：各个包在路上所花时间的**差值变化（忽快忽慢，到达间隔不再均匀）**！如果接收端收到一个包就立刻往喇叭里放，出来的声音就会像鬼畜一样一会儿快进、一会儿卡壳！

#### 2. 治抖神器：播放缓存（Playout Buffer）与两大必考计算模型
怎么把参差不齐到达的分组，重新变成匀速流出的水流？在接收端修一个**蓄水池（播放缓存）**！

* **【计算模型 A：定长推迟播放（消除抖动模型）】**
  * **核心原理**：第 1 个分组到达时，先忍住**不要立刻播放**！让它在缓存里等一会儿，故意引入一个固定的端到端**播放时延 $D_{\text{play}}$**。
  * **公式铁律**：假设第 $i$ 个分组在 $t_{\text{send}}(i)$ 时刻发出，在路上花了 $d_i$ 时间，于 $t_{\text{arr}}(i) = t_{\text{send}}(i) + d_i$ 时刻到达接收端。
    * 如果规定端到端总延迟统一对齐为 $D_{\text{play}}$，那么第 $i$ 个分组**应当被播放的时刻**就是：$t_{\text{play}}(i) = t_{\text{send}}(i) + D_{\text{play}}$；
    * 该分组在缓存里需要**额外等待（驻留）的时间**就是：$w_i = D_{\text{play}} - d_i$；
    * 如果某个分组路上太堵，$d_i > D_{\text{play}}$（即它到达的时刻 $t_{\text{arr}}(i)$ 已经超过了它本该被播放的时刻 $t_{\text{play}}(i)$），这个分组就**迟到作废（未能按时赶上播放）**！
    * **要想让所有分组一个都不迟到**，统一设定的端到端播放时延 $D_{\text{play}}$ 必须至少等于所有分组中经历的**最大网络时延 $\max(d_i)$**！

* **【计算模型 B：蓄水池进出水速率（缓存抽空与注满模型）】**
  * **核心原理**：这就是小学数学的“水池进水管与出水管问题”！
  * 设播放缓存的总容量为 $B_{\max}$，启动播放的水位阈值（积攒到多少数据才开播）为 $B_{\text{start}}$。网络往缓存里灌水的速率（下载速率）为 $R_{\text{in}}$，播放器从缓存里抽水读取的速率（播放消耗速率）为 $R_{\text{out}}$：
    1. **开播前的预缓冲时间**：此时只进不出，水位从 $0$ 涨到 $B_{\text{start}}$ 所需时间 $t_0 = \frac{B_{\text{start}}}{R_{\text{in}}}$；
    2. **情况一：下载比播放慢（$R_{\text{in}} < R_{\text{out}}$，入不敷出）**：
       * 开播后，缓存水位以净消耗速率 $(R_{\text{out}} - R_{\text{in}})$ 不断下降！
       * 原本积攒的 $B_{\text{start}}$ 水量能撑多久才被彻底抽干（暂停卡顿）？
         $$t_{\text{play}} = \frac{B_{\text{start}}}{R_{\text{out}} - R_{\text{in}}}$$
       * 抽干暂停后，播放器停止抽水，网络以 $R_{\text{in}}$ 重新灌满到 $B_{\text{start}}$ 才能恢复播放，暂停等待时间为 $t_{\text{pause}} = \frac{B_{\text{start}}}{R_{\text{in}}}$。
    3. **情况二：下载比播放快（$R_{\text{in}} > R_{\text{out}}$，供大于求）**：
       * 开播后，缓存水位不仅不会降，反而以净增长速率 $(R_{\text{in}} - R_{\text{out}})$ 继续往上涨！
       * 从水位 $B_{\text{start}}$ 涨满到整个缓存上限 $B_{\max}$ 需要多久？
         $$t_{\text{fill}} = \frac{B_{\max} - B_{\text{start}}}{R_{\text{in}} - R_{\text{out}}}$$
         *(若问从最开始空缓存下载算起直到装满的总时间，别忘了加上开播前预缓冲的 $t_0 = \frac{B_{\text{start}}}{R_{\text{in}}}$！)*

### 二、 流媒体工作的全套流程与“协议三剑客”（RTSP / RTP / RTCP）

当你在网页上点开一段在线视频时，后台其实发生了极其精妙的“四步交接班”：
1. **第一步（拿导游图）**：你的浏览器先用 **`HTTP`** 从普通万维网服务器上下载一个极小的文本文件，叫**元文件（Metafile）**（里面写着音视频真正存放在哪台流媒体服务器上），浏览器把元文件交给本地的**媒体播放器**。
2. **第二步（拿遥控器发号施令 —— `RTSP` 实时流式协议）**：
   * 媒体播放器根据元文件里的地址，直接找**媒体服务器（流式服务器）**建立连接，使用的是应用层的 **`RTSP`（Real-Time Streaming Protocol）**。
   * **必考定位**：**RTSP 自己绝对不传输一丁点音视频数据！** 它只是一个**带外控制协议**（就像电视机的红外遥控器），专门负责发送“播放（PLAY）、暂停（PAUSE）、快进、快退、结束（TEARDOWN）”等控制命令（RTSP 既可以用 TCP 也可以用 UDP）。
3. **第三步（装盒运送音视频数据 —— `RTP` 实时运输协议）**：
   * 媒体服务器收到 RTSP 的播放指令后，把压缩好的音频/视频块装进 **`RTP`（Real-time Transport Protocol）** 分组里，再把 RTP 塞进 **`UDP`** 数据报（再套上 IP）源源不断地发给播放器。
   * **RTP 首部的三大法宝（必背）**：
     * **①序号（16位）**：每发一个 RTP 包加 1，让接收端能**发现有没有丢包，并把乱序到达的包重新排好队**；
     * **②时间戳（32位）**：记录该数据包第 1 个字节的**采样时刻**（注意：时间戳的时钟刻度必须与采样周期对齐，比如 $8000\text{ Hz}$ 语音每 $125\ \mu\text{s}$ 跳 1 下），让接收端精准算出包与包之间原本的时间间隔以**消除抖动**；
     * **③标记（Marker）**：标出一段话音突发的开始或一帧视频画面的边界。
   * **封装开销计算提示**：算 VoIP 语音通话的实际网络发送速率时，如果每隔 $T$ 秒打包一次，每秒就要发 $N = \frac{1}{T}$ 个分组；每个分组除了原始话音字节外，还要层层套上 **$12\text{ B}$ 的 RTP 首部 + $8\text{ B}$ 的 UDP 首部 + $20\text{ B}$ 的 IP 首部（共 $40\text{ B} = 320\text{ bit}$ 的固定首部开销）**！
4. **第四步（路况监督与音画同步 —— `RTCP` 实时运输控制协议）**：
   * 与 RTP 成对工作（同样跑在 UDP 上），自己也不传音视频数据，专门干三件事：①向发送端**周期性汇报接收质量**（丢包率、最大抖动），让服务器在网堵时自动把高清切为标清；②把同一个主播发出的**音频流和视频流的时间戳绑定同步**（防止口型对不上声音）；③标识多播组成员。
   * **5% 铁律**：为了防止汇报路况的 RTCP 把传输视频的 RTP 给挤占了，规定 **RTCP 占用的总带宽绝不能超过整个会话总带宽的 $5\%$**！

### 三、 路由器怎么照顾音视频 VIP？（排队调度三大算法：FIFO / FQ / WFQ）

为了改善服务质量（QoS），路由器在把分组往出口链路上发时，有三种排队调度策略：
1. **先进先出（FIFO）**：所有业务排成一队，谁先到谁先走。实现最简单，但如果前面有个 FTP 下载大包堵着，后面的实时语音小包就只能干等（毫无服务质量区分）。
2. **公平排队（FQ）**：给每个业务流单独立一个队列，路由器出口像发牌一样轮流从每个队列里取 1 个包发送。但为了防止发长包的人占便宜，采用**“逐字节轮询”**思想计算每个包的虚拟完成时间，谁先算完谁先发。缺点是对所有队列一视同仁，不能给高优先级视频流分配更多带宽。
3. **加权公平排队（WFQ，考纲高频计算点！）**：
   * 给每个队列分配不同的**权重 $w_i$**（比如队列1权重 $0.6$，队列2权重 $0.2$，队列3权重 $0.2$，比例为 $3 : 1 : 1$）。
   * 当所有队列都有包时，严格按权重比例循环服务（每发 5 个包里，队列1占 3 个，队列2、3各占 1 个）。
   * **工作保守性（Work-Conserving，必考！）**：如果某一时刻队列 2 空了（没有包），路由器**绝对不会站在那儿发呆空等**！剩下的队列 1 和队列 3 会立刻按照它们原本的权重比（$0.6 : 0.2 = 3 : 1$）瓜分全部带宽（即变成每发 4 个包里，队列1发 3 个、队列3发 1 个）！

## 模块三：第9章 无线局域网 IEEE 802.11（对应 816 考纲 三(五)2、三(六)3）

> **考纲要求**：三(五)2 随机访问：`CSMA/CA` 协议；三(六)3 局域网：`IEEE 802.11`。

### 一、 为什么无线网绝对不能照搬有线网的 CSMA/CD？

在有线以太网（`802.3`）里，大家靠一根铜线连在一起，用的是 **CSMA/CD（边发送、边监听碰撞）**。但到了无线局域网（`802.11` Wi-Fi），CSMA/CD 彻底失灵了，原因有三点：
1. **硬件上“自己震聋自己”**：无线电波在空气中随距离衰减极快。当无线网卡正在往外发射信号时，自己天线口那几万倍强度的发射功率会把远处传来的微弱碰撞信号彻底淹没，硬件上根本做不到“边发送边检测碰撞”。
2. **隐蔽站问题（Hidden Station Problem）**：
   * 想象站点 A 和站点 C 中间隔了一堵厚承重墙（或者相距太远），A 和 C 互相听不见对方的无线信号；但基站 AP（或接收站 B）正好站在它俩中间，谁说话 B 都能听见。
   * 当 A 正在给 B 发数据时，C 竖起耳朵听了一圈空气，发现“咦？一片安静啊！”，于是 C 也同时开口给 B 发数据——两股电波在 B 的天线上撞得粉碎！这就叫**隐蔽站问题**。
3. **暴露站问题（Exposed Station Problem）**：
   * 四个人排成一排：$A \leftarrow B \quad C \rightarrow D$。B 正在给左边的 A 说话，站在 B 旁边的 C 听到了 B 的声音，误以为空气信道忙，就不敢给右边的 D 说话了——其实 C 给 D 说话根本不会干扰左边的 A 听 B 说话！这导致信道利用率白白浪费。

因此，802.11 彻底放弃了“碰撞检测（CD）”，改为**“碰撞避免（CSMA/CA）” + “链路层逐帧停止等待确认（ACK）”**！

---

### 二、 CSMA/CA 的四大核心设计（考场大题与单选的命脉）

既然空中极易出错又没法边发边听碰撞，802.11 设计师设计了环环相扣的四套机关：

#### 机关 1：帧间间隔（IFS）的等级森严 —— 让重要的人先走！
无线网规定：哪怕你听到空中没声音（信道空闲），也**绝对不准立刻开口说话**，必须先憋一口气等一段“帧间间隔”！按照长短分为两档最核心的间隔：
* **`SIFS`（短帧间间隔，最短！）**：专门留给**必须立刻回应的紧急控制帧**（比如收到数据后立刻回发的 **`ACK` 确认帧**、收到预约请求后立刻回发的 **`CTS` 帧**）。因为 SIFS 极短，别人还在等漫长的 DIFS 呢，你的 `ACK` 就已经抢先把话接过去了，谁也打断不了正在进行的对话！
* **`DIFS`（分布协调功能帧间间隔，比 SIFS 长得多！）**：凡是想发起**新的一轮数据帧（或 RTS）发送**的普通站点，检测到信道空闲后都必须老老实实等够长长的 `DIFS`。

#### 机关 2：二进制指数退避与“计时器冻结”规则
* **什么时候不用退避、什么时候必须退避？**
  * 如果一个站点突然有数据要发，一听信道本来就是空闲的，且持续空闲超过了 `DIFS`，它可以**立即发送**！
  * 但如果它一听信道正忙（或者这是重传帧、连续发送的第二帧），等信道刚忙完并熬过 `DIFS` 后，此时周围可能好几个站点都憋着劲想同时抢答！为了防止大家在 `DIFS` 结束的同一微秒撞车，所有等待站点必须摇号选一个随机退避时间倒计时。
* **计时器冻结规则（必考细节！）**：
  * 假设你摇到了倒计时 $10$ 个时隙，刚倒数了 $3$ 个时隙（还剩 $7$ 个），突然旁边有个倒数更短的老兄抢先开口发数据把信道占了！
  * 这时候你的倒计时**立刻暂停（冻结在剩余的 $7$ 上）**！等那个老兄发完数据、收完 `ACK`、信道再次空闲满一个 `DIFS` 后，你**不需要重新摇号，而是直接从刚才冻结的 $7$ 继续往下倒数**！这样保证了越早开始排队的站点越早发出去，对所有站点最公平！

#### 机关 3：解决隐蔽站的终极杀招 —— RTS / CTS 信道预约与 NAV（虚拟载波侦听）
为了治好前面说的“隐蔽站 C 听不见 A 说话而偷袭 B”的问题，802.11 引入了可选的“举手预约制”（由于预约本身也耗时间，通常只在发送较长的数据帧时启用）：
1. **A 发 `RTS`（请求发送，20字节极短帧）**：A 等完 `DIFS` 后，先不发长数据，而是发一个极短的 `RTS` 帧给 B，里面大声喊道：“我要给 B 发长数据啦！接下来从发 `CTS`、发 `DATA` 一直到我收完 `ACK`，总共还要霸占信道 $T_1$ 微秒！”
2. **B 回 `CTS`（允许发送，14字节极短帧）**：B 收到后，只等一个极短的 `SIFS`，就向四周广播回一个 `CTS` 帧：“准奏！接下来从发 `DATA` 一直到收完 `ACK`，还要霸占信道 $T_2$ 微秒！”
3. **全场闭嘴（设置 `NAV` 网络分配向量）**：
   * 哪怕隐蔽站 C 离 A 太远没听见 `RTS`，但 C 离 B 近啊，**C 一定能清清楚楚地听见 B 广播的 `CTS`！**
   * 凡是听见 `RTS` 或 `CTS` 的其他吃瓜站点，都会把帧里写的“剩余占用时间”抄到自己脑门上的免打扰倒计时器里（这个倒计时器就叫 **`NAV` 网络分配向量**）。在 `NAV` 倒计时归零之前，哪怕吃瓜站点用天线听着空气里好像没声音，也**绝对不准去争用信道**（这叫**虚拟载波侦听**）！

#### 机关 4：一次完整 RTS/CTS 成功传输的时间轴总账（必背公式模板！）
把上面整个预约到确认的过程画成一条时间轴（忽略极短的电磁波空中传播时延），你会发现它永远由 **“1 个 DIFS + 3 个 SIFS + 4 个帧的发送时间”** 严丝合缝地拼接而成：

$$\text{从决定发送到收到 ACK 的总时间 } T_{\text{total}} = \text{DIFS} + T_{\text{RTS}} + \text{SIFS} + T_{\text{CTS}} + \text{SIFS} + T_{\text{DATA}} + \text{SIFS} + T_{\text{ACK}}$$

并且从这条时间轴上，一眼就能看出 `RTS` 和 `CTS` 帧里填写的预约时间（即 `NAV` 值）有多长（**就是它自己发完之后，后面还剩多少项，就把后面剩下的项全加起来！**）：
* **`RTS` 帧里填的持续时间 $\text{NAV}(\text{RTS})$**（RTS 发完后还剩 3 个 SIFS 和 CTS、DATA、ACK 三帧）：
  $$\text{NAV}(\text{RTS}) = 3 \times \text{SIFS} + T_{\text{CTS}} + T_{\text{DATA}} + T_{\text{ACK}}$$
* **`CTS` 帧里填的持续时间 $\text{NAV}(\text{CTS})$**（CTS 发完后还剩 2 个 SIFS 和 DATA、ACK 两帧）：
  $$\text{NAV}(\text{CTS}) = 2 \times \text{SIFS} + T_{\text{DATA}} + T_{\text{ACK}}$$
*(注：每个帧的发送时间 $T_{\text{帧}} = \frac{\text{帧字节数} \times 8}{\text{对应发送速率}}$，把这个时间轴印在脑子里，任何 802.11 计算大题都是送分题！)*

### 三、 802.11 MAC 帧的“三地址迷局”（为什么无线帧要有 3 个 MAC 地址？）

在有线以太网（`802.3`）里，一个帧只有 2 个 MAC 地址（目的 MAC、源 MAC）。但当你用手机连上学校的无线接入点 **AP**，给连在学校路由器 **$R$** 上的教务系统发包时，由于 **AP 是一个只工作在数据链路层的“无线网桥”（它没有 IP 地址，也不拆改 IP 包，只负责把 `802.11` 无线帧翻译成 `802.3` 有线帧交给路由器 $R$）**，就会出现一个有趣的问题：
* 在空中飞行的这一跳无线路上，无线电波的**直接发送人**和**直接接收人**分别是手机和 AP；
* 但等 AP 把这个帧转成有线以太网帧发给路由器 $R$ 时，AP 必须知道**这个帧最终要交给有线网里的哪台路由器接口（或 originally 是从哪台有线设备发来的）**！

因此，有固定基础设施的 802.11 数据帧首部里启用了 **3 个 MAC 地址字段（地址 1、地址 2、地址 3）**，记住下面这句万能口诀，1秒填出所有地址：

> **万能口诀**：**“地址 1 永远是当前这一跳无线电波的【直接接收者】；地址 2 永远是当前这一跳无线电波的【直接发送者】；地址 3 永远是帮你过桥的那个【幕后第三者（路由器接口或远端主机 MAC）】！”**

我们用这个口诀看两个方向的实例（设你的手机为 $H_1$，无线接入点为 $\text{AP}$，连接外网的路由器接口为 $R$）：
1. **方向一：手机 $H_1$ 发数据，经由 $\text{AP}$ 发往路由器 $R$（`去往 AP = 1, 来自 AP = 0`）**：
   * 这一跳电波是谁收？$\text{AP}$ 收！所以 **地址 1 = $\text{AP}$ 的 MAC 地址**；
   * 这一跳电波是谁发？手机 $H_1$ 发！所以 **地址 2 = 手机 $H_1$ 的 MAC 地址**；
   * 幕后第三者（最终要交给谁）？路由器 $R$！所以 **地址 3 = 路由器 $R$ 的 MAC 地址**。
2. **方向二：路由器 $R$ 发来有线帧，由 $\text{AP}$ 转成无线帧发给手机 $H_1$（`去往 AP = 0, 来自 AP = 1`）**：
   * 这一跳电波是谁收？手机 $H_1$ 收！所以 **地址 1 = 手机 $H_1$ 的 MAC 地址**；
   * 这一跳电波是谁发？$\text{AP}$ 发！所以 **地址 2 = $\text{AP}$ 的 MAC 地址**；
   * 幕后第三者（原本是谁交给 AP 的）？路由器 $R$！所以 **地址 3 = 路由器 $R$ 的 MAC 地址**。
