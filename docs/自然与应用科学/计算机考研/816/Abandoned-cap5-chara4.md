## 一、 运输层的存在意义与 UDP 底层逻辑（共 8 题）

### 1. `5-01` 试说明运输层在协议栈中的地位和作用。运输层的通信和网络层的通信有什么重要区别？为什么运输层是必不可少的？

* **【说人话】**：假设你的电脑上同时开着微信、B站和浏览器。网络层（IP）就像只会看“大学校门地址”的货车司机，它把包裹扔进东南大学传达室（你的网卡）就算完事了；如果没有运输层（TCP/UDP）充当“传达室分拣员”，看着包裹上的**端口号**把视频包送给B站、把聊天包送给微信，你电脑里的几十个软件就会把收到的二进制数据抢成一锅粥！

* **【严谨考场结论】**：

  * **地位与作用**：运输层处于面向通信部分的最高层，同时也是用户功能中的最低层，向它上面的应用层提供端到端的逻辑通信服务。

  * **核心区别（必考单选考点）**：**网络层**为**不同主机（Host-to-Host）**之间提供逻辑通信；而**运输层**为运行在不同主机上的应用进程（Process-to-Process / 端到端）之间提供逻辑通信。

  * **为什么必不可少**：计算机中往往同时运行多个应用进程，必须依靠运输层的**端口复用（Multiplexing）和分用（Demultiplexing）**功能才能将数据准确交付给对应的应用进程；同时运输层还要对收到的报文进行**差错检测**（IP 层首部检验和根本不检查数据载荷是否出错！），并按需提供可靠传输。

### 2. `5-03` 当应用程序使用面向连接的 TCP 和无连接的 IP 时，这种传输是面向连接的还是无连接的？

* **【说人话】**：你在淘宝买东西，你跟客服是“一对一确认好才发货（面向连接的 TCP）”，哪怕顺丰在底层运快递时每辆卡车是“哪条路空走哪条路（无连接的 IP）”，对你和卖家来说，这笔交易依然是严格按合同走完的。

* **【严谨考场结论】**：**这取决于从哪一层来看——在运输层（及应用层看来）是面向连接的，而在网络层则是无连接的**。应用程序直接调用的是运输层 TCP 提供的服务接口，因此对应用程序而言，它获得的就是**面向连接的可靠传输服务**；至于下层 IP 采用无连接数据报独立选路，对上层是完全透明（不可见）的。

### 3. `5-05` 试举例说明有些应用程序愿意采用不可靠的 UDP，而不愿意采用可靠的 TCP。

* **【说人话】**：打王者荣耀或微信语音通话时，1秒钟前的那帧画面如果丢了，你希望网络卡住半秒钟去重传1秒前的旧画面，还是直接跳过旧画面、把最新的画面播出来？当然是后者！TCP 那套“三次握手建连接 + 丢包必须停下来重传 + 拥塞控制自动降速”的好心肠，在实时音视频和快速查询眼里全都是拖后腿的累赘。

* **【严谨考场结论（四大典型场景）】**：

  1. **实时多媒体应用（如 IP 电话、实时视频会议、直播流媒体）**：要求极低的时延，能容忍少量丢包，而 TCP 的超时重传和拥塞控制降速会导致严重的画面卡顿与时延抖动。

  2. **一次性简短请求/应答应用（如 DNS 域名查询、SNMP 网络管理）**：只需一问一答两个包即可完成；若用 TCP，光三次握手和四次挥手就要额外多发 7 个报文段、多等好几个 RTT，开销过大。

  3. **多播与广播应用（如 RIP 路由广播、DHCP 广播发现、IPTV 视频多播）**：TCP 严格只能是一对一（点对点）连接，**根本不支持一对多（多播）和一对全体（广播）**，此类应用只能使用 UDP。

  4. **特定时期或资源受限应用（如 TFTP 无盘引导、网络拥塞时的 SNMP 告警）**：UDP 代码极简、首部仅 8 字节，无连接状态开销。

### 4. `5-06` 接收方收到有差错的 UDP 用户数据报时应如何处理？

* **【说人话】**：闷不吭声直接扔进垃圾桶（或贴个“此包有毒”的条子交给应用程序），绝不给发送方打电话让它重发。

* **【严谨考场结论】**：接收方 UDP 计算检验和发现差错后，采取直接静默丢弃（Discard）的办法（也可将该受损数据报连同差错警告一起交给应用程序处理），**不向发送方发回任何差错报告，也不要求重传**。

### 5. `5-07` 如果应用程序愿意使用 UDP 完成可靠传输，这可能吗？请说明理由。

* **【说人话】**：完全可以！UDP 虽然自己是个“甩手掌柜”，但它并没有禁止你在它上面的**应用层代码**里自己写一套“编号 + 发确认收条 + 定时重传”的逻辑（比如 TFTP 协议，以及现在火遍全球的 HTTP/3 底层的 QUIC 协议，全都是在 UDP 上面自己实现了可靠传输！）。

* **【严谨考场结论】**：**可能**。只要**由应用程序自己在应用层实现可靠传输所需的全部机制**（如添加应用层报文序号、接收端确认应答 ACK、超时重传计时器、滑动窗口与缓存排序等），就可以在无连接的 UDP 之上完成可靠传输（典型实例：**TFTP 简单文件传送协议**、以及现代 **QUIC / HTTP/3** 协议）。

### 6. `5-10` 试说明运输层中伪首部的作用。

* **【说人话】**：万一中间某台糊涂路由器把你的 IP 数据报首部里的“目的 IP 地址”改错了，结果本该发给张三的包阴差阳错送到了李四的电脑上。如果 UDP/TCP 算检验和时只看运输层自己的头和数据，李四的 UDP 根本发现不了“这包其实是寄给张三的”！所以在算检验和时，临时把 IP 首部里的**源 IP、目的 IP、协议号**借过来拼在前面一起算——到了李四那儿，李四拿自己的 IP 一算检验和，对不上，当场识破“送错门了”！

* **【严谨考场结论】**：**伪首部（Pseudo-Header，共 12 字节：含 32位源IP、32位目的IP、8位全0、8位协议号、16位TCP/UDP长度）**既不向下传送也不向上递交，**仅仅是为了计算运输层（UDP/TCP）检验和而临时添加的**。其核心作用是**双重校验**：既检查运输层报文段本身在传输中是否出现比特差错，又同时向运输层验证**网络层是否将该分组投递到了正确的目的主机 IP 地址，且协议字段（UDP=17 / TCP=6）未被篡改**。

### 7. `5-11` 某个应用进程使用运输层的用户数据报 UDP，然后继续向下交给 IP 层后，又封装成 IP 数据报。既然都是数据报，是否可以跳过 UDP 而直接交给 IP 层？哪些功能 UDP 提供了但 IP 没有提供？

* **【说人话】**：IP 数据报首部里只有“源主机 IP”和“目的主机 IP”，根本没有“端口号”这个格子！如果你跳过 UDP 直接把数据塞给 IP 层，对面的电脑收到 IP 包拆开一看，满脸问号：“这电脑上跑着 50 个程序，我到底该把这个包塞给谁？”

* **【严谨考场结论】**：**通常不能跳过 UDP 直接交给 IP 层**。UDP 提供了但 IP 层没有提供的两项关键功能：

  1. **对应用进程的端口分用与复用功能（最重要的区别）**：IP 数据报首部只能标识源主机和目的主机，只有协议号而**没有端口号**；必须依靠 UDP 首部中的 **16位源端口和 16位目的端口**，操作系统才能把收到的数据准确交付给主机内特定的应用进程。

  2. **对数据载荷部分的差错检测功能**：IPv4 首部检验和**只检验 IP 首部**，不检验数据部分；而 UDP 的检验和**覆盖了整个 UDP 首部和全部应用数据载荷（含伪首部）**。

### 8. `5-15` 使用 TCP 对实时话音数据的传输有什么问题？使用 UDP 在传送数据文件时会有什么问题？

* **【严谨考场结论】**：

  * **用 TCP 传实时话音的问题**：当网络出现丢包时，TCP 会强制启动**超时重传或快重传**，并触发**拥塞控制大幅减小发送窗口（降低发送速率）**；接收端还必须等丢失的旧分组重传补齐后才能按序向上交付，这会造成实时语音出现严重的**停顿、卡顿和不可接受的极大时延**。

  * **用 UDP 传数据文件的问题**：数据文件（如程序安装包、文档）要求每一个字节都绝对准确无误；而 UDP 不提供确认重传、流量控制和拥塞控制，一旦网络拥塞或干扰导致哪怕 1 个 UDP 分组丢失、乱序或出错被丢弃（且应用程序自己未写重传逻辑），整个接收到的文件就会**残缺损坏而无法使用**。

## 二、 停止等待协议与 TCP 首部精妙设计（共 9 题）

### 9. `5-16` 在停止等待协议中如果不使用编号是否可行？为什么？

* **【说人话】**：假设你不给包裹编号。你发了第1箱苹果，对面收到了并给你寄了张“收到”的回执；结果这张回执在路上堵车超时了，你以为苹果丢了，又重发了一箱一模一样的苹果！对面收到第二箱苹果时，因为包裹上没写“这是第1号还是第2号”，它根本分不清你是“因为没收到回执而重发的第1箱”，还是“新买的第2箱”，结果收下了两箱重复的苹果！

* **【严谨考场结论】**：**不可行**。当数据报文段本身在网络中滞留重传，或者**确认报文段（ACK）丢失/迟到导致发送方超时重传**时，接收方会收到两个内容完全相同的报文段。如果不使用分组编号（哪怕只需 `0` 和 `1` 交替的 1 比特编号），接收方将**无法区分当前收到的报文段是“新的下一分组”还是“因确认丢失而重传的旧重复分组”**，从而导致数据重复交付错误。

### 10. `5-17` 在停止等待协议中，收到重复的报文段时不予理睬（即悄悄地丢弃它而其他什么也不做）是否可行？试举出具体例子说明理由。

* **【说人话】**：绝对不行！思考一下：**对方为什么会像个复读机一样给你重发它明明已经发过的旧包裹？原因只有一个——你上次发给它的那张“确认收条 ACK”在半路上丢了！** 如果你这次把重复包裹悄悄扔掉、并且死活不补发一张确认收条，对方就会以为包裹又丢了，永远在那儿一遍接一遍地死循环重传！

* **【严谨考场结论】**：**绝对不可行！**

  * **具体反例**：设 A 发送报文段 $M_0$，B 正确收到 $M_0$ 后发回确认 $\text{ACK}_0$，但 $\text{ACK}_0$ **在传输途中丢失了**。A 超时未收到确认，于是重传 $M_0$。此时 B 收到了重复的 $M_0$，如果 B 仅仅悄悄丢弃该重复的 $M_0$ 而不再次向 A 发送确认 $\text{ACK}_0$，那么 **A 将永远收不到对** $M_0$ **的确认，从而陷入无限次超时重传** $M_0$ **的死锁状态**，协议彻底卡死！

  * **正确做法**：收到重复报文段时，必须**先丢弃该重复报文段，同时立即再次向发送方发送对该报文段的确认（ACK）**！

### 11. `5-18` 停止等待协议中“早先滞留的旧重传包 $M_0$ 与迟到确认”导致协议失败的时空图原理（为什么 TCP 后面要引入 32位大序号和 $2\text{MSL}$？）。

* **【说人话】**：这道题揭示了为什么简单的 `0/1` 交替编号在复杂的互联网路由里会翻车：如果旧的 $M_0$ 没死透（在某台慢速路由器里迷路兜圈子），而此时你已经发完了 $M_1$、开始发下一轮同样叫 $M_0$ 的新包了，偏偏新 $M_0$ 丢了、当年迷路的那个旧幽灵 $M_0$ 突然冒出来顶替了新 $M_0$，接收方就会把旧货当新货收下！

* **【严谨考场结论】**：

  * **交换过程描述**：①A 发 $M_0$，超时未收到确认，重传 $M_0$（记为 $M_0'$，该 $M_0'$ 在网络中严重滞留）；②不久 A 收到对第一次 $M_0$ 的迟到确认，于是 A 发送 $M_1$ 并顺利收到对 $M_1$ 的确认；③接着 A 发送下一轮序号回绕后的**新** $M_0$**（记为** $M_0''$**）**，但新 $M_0''$ 在途中丢失；④恰在此时，第①步中滞留在网络里的**旧重传包** $M_0'$ 到达了 B，B 此时正期待序号为 $0$ 的分组，无法分辨这是上一轮的旧 $M_0'$ 还是这一轮的新 $M_0''$，于是错误地收下了旧 $M_0'$。

  * **工程解决之道**：这正是为什么 TCP 不能只用 1 比特编号，而必须采用 **32位超大序号空间（**$2^{32}$ **字节）** 并配合 IP 层 **最大生存时间 MSL（TTL限制）**，确保旧序号分组在序号发生绕回之前早已在网络中超时消亡！

### 12. `5-25` 为什么在 TCP 首部中要把 TCP 的端口号放入最开始的 4 个字节？

* **【说人话】**：为了救命的时候能看清这包是谁发的！当网络断路或端口没开，路由器或主机要发回 **ICMP 差错报告报文** 时，ICMP 规范规定只截取出错 IP 数据报的“IP首部 + IP数据载荷的前 8 个字节”装进差错包退回给源主机。把源端口和目的端口放在 TCP 首部（以及 UDP 首部）最开头的 4 个字节，源主机收到退回来的那 8 个字节残骸时，一眼就能读出端口号，知道该通知哪个应用程序报错！同时，网络级防火墙和 NAPT 设备在高速查表时也只需要读前 4 个字节。

* **【严谨考场结论】**：

  1. **配合 ICMP 差错报告定位进程**：ICMP 差错报告报文只封装出错 IP 数据报的首部及其后面运输层首部的**前 8 个字节**。将 16位源端口和 16位目的端口固定放在 TCP（和 UDP）首部最开始的 4 个字节内，可确保源主机收到 ICMP 差错报文时能从中提取出端口号，进而通知对应的上层应用进程。

  2. **加速路由器、防火墙与 NAT 处理**：固定在最开头 4 字节便于包过滤防火墙和 NAPT 路由器用硬件在固定偏移位置极速提取端口号。

### 13. `5-26` 为什么在 TCP 首部中有一个“首部长度（数据偏移）”字段，而 UDP 的首部中就没有这个字段？

* **【说人话】**：UDP 的首部永远是雷打不动的 **8 个字节**，多一分没有、少一分不存，谁都知道从第 9 个字节起就是数据，写个长度字段纯属脱裤子放屁；而 TCP 首部除了 20 字节固定部分外，后面还可以挂 $0 \sim 40\text{ B}$ 不等的**选项（Options，如 MSS、窗口扩大、时间戳）**，总长在 $20 \sim 60\text{ B}$ 之间变来变去，不写清楚“首部到底有多长”，接收方根本不知道数据从第几个字节开始！

* **【严谨考场结论】**：**UDP 首部长度是固定不变的 8 字节**，接收方直接从第 9 字节即可读取数据，无需使用字段指明首部长度；而 **TCP 首部除 20 字节固定首部外，还包含长度可变的选项字段（最长 40 字节，使 TCP 首部长度在** $20 \sim 60$ **字节之间变化）**，因此必须设置 4 位的“数据偏移（即首部长度，以 **4字节** 为单位）”字段，用来指明 TCP 报文段的数据起始处距离 TCP 报文段起始处有多远。

### 14. `5-27` 一个 TCP 报文段的数据部分最多为多少字节？为什么？如果用户要传送的数据的字节长度超过 TCP 报文段中的序号字段可能编出的最大序号，问还能否用 TCP 来传送？

* **【严谨考场结论】**：

  * **(1) 单个 TCP 报文段的数据部分理论最大值**：受限于下层 **IPv4 数据报首部中的 16 位“总长度”字段（最大值为** $2^{16} - 1 = 65535$ **字节）**。扣除 IPv4 最小固定首部 $20\text{ B}$ 和 TCP 最小固定首部 $20\text{ B}$ 后，一个 TCP 报文段的数据部分最多为：


  $65535 - 20 - 20 = \mathbf{65495\text{ 字节}}$

  *(注：在实际以太网中，受限于链路层* $\text{MTU} = 1500\text{ B}$*，通常将最大报文段长度* $\text{MSS}$ *设为* $1500 - 20 - 20 = 1460\text{ B}$ *以避免分片)*。

  * **(2) 超过最大序号能否用 TCP 传送**：**完全可以！** TCP 的 32 位序号字段是对字节流进行**模** $2^{32}$ **循环编号（序号绕回 Wrap-around）**的。当字节序号达到**$2^{32} - 1$**后，下一个字节的序号会自动回到**$0$**重新开始循环编号；只要旧序号的报文段在网络中已超过最大生存时间 MSL 消亡（或在高速网中配合 TCP 首部 32 位**时间戳选项 PAWS 防绕回机制**），TCP 就可以无限制地传送任意大小的超大文件（如几十 GB 的蓝光电影）。

### 15. `5-28` 主机 A 向主机 B 发送 TCP 报文段，首部中的源端口是 $m$ 而目的端口是 $n$。当 B 向 A 发送回信时，其 TCP 报文段的首部中的源端口和目的端口分别是什么？

* **【严谨考场结论】**：B 向 A 发送回信时，源端口和目的端口正好对调——**源端口是** $n$**，目的端口是** $m$。

### 16. `5-29` 在使用 TCP 传送数据时，如果有一个确认报文段丢失了，也不一定会引起与该确认报文段对应的数据的重传。试说明理由。

* **【说人话】**：假设你给B连发了第1号包和第2号包。B收到第1号包发回的“第1号收条”在半路丢了；但紧接着0.01秒后，B收到了你的第2号包，发回了“前2号包全都收齐了”的总收条，并且这张总收条赶在你的第1号包闹钟响（超时）之前送到了你手里！既然知道前2号全齐了，你当然不用再傻乎乎重传第1号包了。

* **【严谨考场结论】**：因为 TCP 采用的是**累积确认（Cumulative Acknowledgment）**机制（确认号 **$N$** 表明到序号 **$N-1$** 为止的所有数据均已正确收到）。如果对前一个报文段的确认丢失了，但只要在发送方的**超时重传计时器到期之前**，发送方收到了接收方发来的**对后续报文段的更高序号的确认报文段**，发送方就能确知前面的数据也已被对方正确收齐，从而取消重传计时器，不会引起重传。

### 17. `5-32` 什么是 Karn 算法？在 TCP 的重传机制中，若不采用 Karn 算法，而是在收到确认时都认为是对重传报文段的确认，那么由此得出的往返时间样本和重传时间都会偏小。试问：重传时间最后会减小到什么程度？

* **【说人话】**：什么叫“重传二义性”？你12:00发了原包，12:05超时重发了重传包，结果12:06收到了一张 ACK——你根本分不清这张 ACK 是对面“收到12:00的原包后慢吞吞寄回来的（真实 RTT = 6分钟）”，还是“收到12:05的重传包后秒回的（真实 RTT = 1分钟）”！

  * 如果你傻乎乎地每次都当成是对重传包的秒回，你就会误以为“哇，网络只要1分钟就到了！”，于是把下一次的超时闹钟 RTO 调短；闹钟越短就越容易提前超时重传，刚一重传又刚好收到对原包的迟到 ACK，你又以为网络只要 0.1 秒……如此恶性循环，你的超时时间 RTO 会一路狂跌趋近于 $0$！

* **【严谨考场结论】**：

  * **Karn 算法核心内容**：**①在计算加权平均往返时间** $\text{RTT}_S$ **时，只要报文段重传了，就不采用其往返时间样本**（消除重传确认二义性）；**②报文段每重传一次，就把超时重传时间** $\text{RTO}$ **增大一些（典型做法是直接加倍：**$\text{RTO}_{\text{新}} = 2 \times \text{RTO}_{\text{旧}}$**，即指数退避）**。

  * **若不采用 Karn 算法且总认为是重传确认的后果**：测得的样本 RTT 是从“发出重传报文段”到“收到（实际上是对原报文段的）确认”之间的极短时间差。这会导致计算出的 $\text{RTO}$ 不断缩小，进而使后续报文段更早发生不必要的超时重传，测量出的时间差进一步逼近于 $0$，最终导致 **重传时间** $\text{RTO}$ **无限减小并趋近于** $0$**（或减小到系统设定的最小下限值）**，引发全网重传风暴。

## 三、 TCP 连接释放、状态机与 UDP 边界细节（共 11 题）

### 18. `5-42` 在连接释放（四次挥手）过程中，在 `ESTABLISHED` 状态下，B 收到 A 的 `FIN` 后能否先不发送 `ack = u + 1` 的确认？（因为后面 B 要发送的连接释放 `FIN` 报文段中仍有 `ack = u + 1` 这一信息。）

* **【说人话】**：为什么握手是 3 次（中间的 `SYN` 和 `ACK` 合二为一了），而挥手偏偏要拆成 4 次？因为 A 说“我没话说了（发 `FIN`）”的时候，B 手里可能还有半截文件没传完呢！如果 B 为了省一个包，非要等自己把剩下半截文件全传完、准备发 B 自己的 `FIN` 时才顺便确认 A 的 `FIN`，那 A 的超时闹钟早就响了，A 会以为自己的 `FIN` 丢了而不停重传 `FIN`！

* **【严谨考场结论】**：**通常不能（除非 B 恰好也没有任何数据要发送、可以立即关闭连接）**。

  * **理由**：TCP 连接是全双工的。当 A 发送 `FIN` 主动关闭 A 到 B 方向的连接时，B 到 A 方向的半连接仍处于打开状态，**B 可能还有许多未发完的数据需要继续发送给 A**，从 B 收到 `FIN` 到 B 发送完所有剩余数据并调用关闭发出自己的 `FIN`，中间可能间隔较长时间。如果 B 不立即先发回 `ack = u + 1` 的确认，**A 的重传计时器就会超时，导致 A 反复重传 `FIN` 报文段**。

### 19. `5-43` 在 TCP 有限状态机（图 5-30）中，在什么情况下会发生从状态 `SYN-SENT` 到状态 `SYN-RCVD` 的变迁？

* **【说人话】**：正常情况下，客户端主动发 `SYN` 进入 `SYN-SENT`，收到服务器的 `SYN+ACK` 直接跳进 `ESTABLISHED`；只有一种罕见情况会从 `SYN-SENT` 跳去 `SYN-RCVD`——**两个人同时给对方拨号（同时打开 Simultaneous Open）**！

* **【严谨考场结论】**：发生在通信双方同时主动打开连接（Simultaneous Open）的情况下：主机 A 和主机 B 几乎同时向对方发送 `SYN` 请求报文段，双方都先进入 `SYN-SENT` 状态；随后，处于 `SYN-SENT` 状态的 A 收到了 B 发来的只含 `SYN=1`（不含 `ACK`）的同步报文段，此时 A 就会从 `SYN-SENT` 状态变迁到 `SYN-RCVD`（同步收到）状态，并向对方发回 `SYN + ACK` 确认报文段。

### 20. `5-44` 试以具体例子说明为什么一个运输连接可以有多种方式释放（著名的“两军对垒问题 Two-Army Problem”）。

* **【说人话】**：蓝军 A 和蓝军 B 隔着盘踞在山谷里的红军，要约好明早6点同时冲锋。A 派传令兵送信给 B：“明早6点冲锋！”B 收到后想：“我得派人回信告诉 A 我知道了，不然 A 不敢冲。”A 收到回信后又想：“我得再派人告诉 B‘我已经收到你的回信了’，不然 B 不知道我收没收到，B 还是不敢冲……”由于山谷里的传令兵随时可能被俘虏（网络不可靠），**无论来回发多少封确认信，最后发信的那一方永远无法 100% 确信对方收到了最后一封信**！

* **【严谨考场结论】**：在不可靠的网络上，**不存在能够 100% 保证通信双方在完全绝对可靠的共识下同时释放连接的有限步协议（即“两军问题”无绝对可靠解）**。因此 TCP 连接释放可以通过多种方式结束：①正常的**四报文挥手优雅释放**（配合 $2\text{MSL}$ 计时器）；②若一方只收到 `FIN` 后的确认或最后 `ACK` 丢失，依靠**超时计时器到期后强制进入 `CLOSED` 状态**；③当某一方主机崩溃或遇到严重差错时，直接发送 **`RST`（复位报文段）** 强制异常释放连接。

### 21. `5-50` 图 5-6 计算 UDP 检验和的演算要点。

* **【严谨考场结论】**：将 **12 字节伪首部 + 8 字节 UDP 首部（检验和字段先填全0） + 数据部分（若字节数为奇数则在末尾补1个全0字节凑成偶数字节）** 按每 16 位（2字节）一组进行二进制反码加法（最高位产生的进位必须回卷加到最低位），最后将所得的 16 位和**按位取反**，即为填入 UDP 首部的检验和。

### 22. `5-52` UDP 和 IP 的不可靠程度是否相同？请加以解释。

* **【严谨考场结论】**：**不相同，UDP 的可靠程度略高于 IP（即 IP 比 UDP 更不可靠）**。

  * **理由**：两者虽然都是无连接、尽最大努力交付（不提供确认重传与按序保证），但 **IP 数据报首部检验和只检验 IP 首部本身，完全不检验数据载荷部分是否出错**（数据载荷损坏的 IP 包仍会被交付给上层）；而 **UDP 的检验和（在 IPv4 中默认启用、在 IPv6 中强制启用）覆盖了 UDP 首部、伪首部以及全部应用层数据载荷**，一旦数据载荷出现任何比特差错，UDP 就能检测出来并将其丢弃，不会把错误数据交给应用进程。

### 23. `5-53` UDP 用户数据报的最小长度是多少？用最小长度的 UDP 用户数据报构成的最短 IP 数据报的长度是多少？（单选常考极值题！）

* **【严谨考场结论】**：

  * **UDP 用户数据报的最小长度**（当数据载荷为 $0\text{ B}$，仅含固定首部时）：$8\text{ 字节}$。

  * **构成的最短 IPv4 数据报长度**（加上最小固定 IPv4 首部 $20\text{ B}$）：$20 + 8 = \mathbf{28\text{ 字节}}$。

### 24. `5-57` 某客户有 $67000\text{ 字节}$ 的分组。试说明怎样使用 UDP 数据报传送这个分组。

* **【说人话】**：UDP 首部里的“总长度”字段只有 16 位，最多只能表示 $65535\text{ B}$；而且它底下套着的 IP 数据报总长度最多也只能是 $65535\text{ B}$（扣掉 $20\text{ B}$ IP首部和 $8\text{ B}$ UDP首部，1个 UDP 包最多只能塞进 $65507\text{ B}$ 的数据）！现在你拿来一个 $67000\text{ B}$ 的巨无霸包裹，UDP 是“面向报文、绝不替你切分”的，你要是硬塞给它，它直接给你报错拒收！

* **【严谨考场结论】**：由于受限于 IP 数据报 16 位总长度字段（最大 $65535\text{ B}$），单个 UDP 用户数据报所能携带的应用数据最大长度不能超过 $65535 - 20(\text{IP首部}) - 8(\text{UDP首部}) = \mathbf{65507\text{ 字节}}$。因此，无法将 $67000\text{ B}$ 的数据装入单个 UDP 数据报中发送；**必须由客户应用程序自己在应用层先将该** $67000\text{ B}$ **的数据拆分成两个（或多个）小于** $65507\text{ B}$ **的较小应用报文**，再分别调用 UDP 发送（并在接收端由应用程序自己负责组装还原）。

### 25. `5-63` & `5-64` TCP 有限状态机异常/特殊分支事件状态变迁（配合 `5-62` 构成完整状态机题组）。

* **【严谨考场结论】**：

  * **`5-63`（当前处于 `SYN-RCVD` 同步收到状态）**：

    * **(1) 应用程序主动发送“关闭”命令**：说明在握手还没彻底完成时本地应用就不想连了，TCP **发送一个 `FIN` 报文段**，连接状态变迁为 **`FIN-WAIT-1`（终止等待1）**。

    * **(2) 若在 (1) 之后又收到了对方的 `FIN` 报文段**（即双方同时关闭）：TCP **发送一个 `ACK` 确认报文段**，连接状态从 `FIN-WAIT-1` 变迁为 `CLOSING`（正在关闭）状态。

  * **`5-64`（当前处于 `FIN-WAIT-1` 终止等待1状态）**：

    * **(1) 收到对方对本方 `FIN` 的 `ACK` 确认报文段**：连接状态变迁为 **`FIN-WAIT-2`（终止等待2）**，不发送报文，继续等待对方发来 `FIN`。

    * **(2) 在 `FIN-WAIT-2` 下收到对方的 `FIN` 报文段**：TCP **向对方发送 `ACK` 确认报文段**，启动 $2\text{MSL}$ **时间等待计时器**，连接状态变迁为 `TIME-WAIT`（时间等待）状态。

    * **(3) 经过** $2\text{MSL}$ **时间超时后**：连接状态最终变迁为 `CLOSED`（关闭）状态，连接彻底释放。

### 26. `5-72` & `5-73` TCP 接收窗口前沿与后沿移动法则：为什么严禁“接收窗口前沿向后收缩（Shrinking the Window）”？

* **【说人话】**：假设接收方 B 刚才给发送方 A 拍着胸脯写字条说：“我的确认号是 `ack = 300`，接收窗口是 `rwnd = 600`（也就是说：从 300 号字节到 899 号字节这 600 个空位我都给你留好了，你尽管发过来！）”

  * 听到这话，发送方 A 兴高采烈地一口气把 300 到 899 号字节全发到半路上了。结果下一秒，B 突然反悔了，发了个新字条说：“我刚才不算数，我现在只收 `rwnd = 400`（只收到 699 号）或者直接置为 `rwnd = 0`！”这就叫“接收窗口前沿向后退缩（从 900 倒退回了 700 或 300）”——这下全乱套了，A 已经发出去在路上的 700\~899 号字节到了 B 门口会被当成越界包直接撞死丢弃！

  * 那如果 B 真的想把接收窗口从 600 缩小到 400 甚至 0，正规做法是什么？**“保持右边界（前沿 900）原地不动，等收下 200 字节数据让左边界（后沿 `ack`）从 300 往前走到 500 时，顺势把窗口大小改成 `rwnd = 400`”**！

* **【严谨考场结论】**：

  * **初始基准**：已确认序号为 $300$（即下一个期待序号 / 窗口后沿为 $301$，或按 0 起始约定窗口覆盖 $[300, 899]$），接收窗口大小 $\text{rwnd} = 600$，此时**接收窗口前沿位于序号** $300 + 600 = 900$ **处**。

  * **允许发生的情况（窗口前沿向前推进，或保持前沿不动而缩小窗口）**：

    1. **窗口平移**：收到 $100\text{ B}$ 数据且应用进程立即读走 $100\text{ B}$ $\rightarrow$ 发送 `ack = 400, rwnd = 600`（后沿前移至 400，前沿前移至 1000，允许！）；

    2. **窗口增大**：应用进程腾出更多缓存 $\rightarrow$ 发送 `ack = 300, rwnd = 800`（前沿前移至 1100，允许！）；

    3. **合法地减小接收窗口（前沿不动，后沿前移）**：收到 $200\text{ B}$ 数据但应用进程未读走（缓存减少 $200\text{ B}$） $\rightarrow$ 发送 **`ack = 500, rwnd = 400`**（此时新的窗口前沿仍为 $500 + 400 = 900$，**窗口前沿没有后退**，完全允许！）。

  * **严禁发生的情况（`5-72` & `5-73` 核心结论：TCP 标准强烈不赞成接收窗口前沿向后收缩）**：

    * 例如在未收到新数据时直接发送 `ack = 300, rwnd = 400`（前沿从 900 倒退至 700），或者如 `5-73` 所述直接发送 **`ack = 300, rwnd = 0`**（前沿从 900 猛退回 300）。

    * **原因**：因为发送方可能已经根据此前通告的窗口上限（900）将序号在 $300 \sim 899$ 之间的数据发送到了网络中；若接收方强行将窗口前沿向后收缩，会导致这些已在途中的合法报文段到达接收方时因超出新窗口边界而被错误丢弃，引发协议混乱与无谓重传！
